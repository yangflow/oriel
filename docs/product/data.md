# 数据

数据模型、存储、删除与撤销、保留期限和收藏的本地副本。索引见 [docs/product.md](../product.md)。

## 数据模型

时间都是 Unix 毫秒整数。布尔是 `0` / `1`。

### 源

一条订阅。每个源有一个形态：`article`、`video`、`social`、`image`、`forum`（界面叫“社区”，英文 Community）。条目的形态跟随源：条目表的 `kind` 只是源的形态的副本（见[「条目」](#条目)），改源的形态，条目跟着变。`kind` 的取值由表 `sources` 上的 `CHECK` 约束限定。

| 字段 | 说明 |
|---|---|
| `url` | 订阅地址。RSSHub 源为空串。 |
| `rsshub_path` | RSSHub 路径，以 `/` 开头。普通源为空。抓取时拼上设置里的 RSSHub 根地址，换实例只改设置。源只记路由，不记实例。 |
| `rsshub_instance` | 上次成功抓取的 RSSHub 实例的根地址，从没成功过或不是 RSSHub 源时为空串。每次成功抓取（含 304）都更新。 |
| `title`、`site_url`、`icon_url` | 展示用。 |
| `icon_checked_site` | 上次为找图标而查看过主页的站点地址，见[「抓取」](fetching.md#抓取)。 |
| `kind` | 五种形态之一。 |
| `etag`、`last_modified` | 条件请求用。 |
| `last_fetched_at`、`last_success_at`、`last_error`、`last_error_kind`、`consecutive_failures` | 抓取健康状况。`last_error_kind` 是上次失败原因的稳定代码，界面据此用用户的语言解释；空串是没有失败或没有归类，取值有 `blocked`（站点的机器人防护拦下了抓取）和 `gone`（站点答 410，订阅已被移除），见[「抓取」](fetching.md#抓取)。`last_error` 是原始的英文文字。 |
| `fetch_interval_sec` | 现在用的抓取间隔（秒）。`fetch_interval_auto` 为 0 时是用户定的固定值；为 1 时是上一次成功抓取后算出的自动间隔，没算过时是 900。 |
| `fetch_interval_auto` | 0 或 1，新订阅默认 1：间隔「自动」，见[「抓取」](fetching.md#抓取)。 |
| `full_text` | 开关，默认 `1`。文章形态的源开着时新条目抽取全文，见[「抓取」](fetching.md#抓取)。新订阅的初始值来自设置 `default_full_text`。 |
| `suggested_kind` | 第一次成功抓取后，服务端觉得订阅更像哪种形态（`video`、`image` 或 `forum`），空串表示没有建议。只是建议，不会自己改 `kind`。 |
| `moved_url`、`moved_seen`、`moved_dismissed` | 订阅地址被永久重定向（301、308）的记录，见[「抓取」](fetching.md#抓取)的「永久重定向」：`moved_url` 是连续落到的新地址，空串表示没有；`moved_seen` 是已经连续几次落在它上面；`moved_dismissed` 是用户忽略过的新地址，空串表示没有。默认空串、0、空串。 |
| `feed_title` | 标题上次是从订阅里取来的那个值，用来分辨标题是用户改过的还是一直跟着订阅走的，见[「抓取」](fetching.md#抓取)第 9 条。默认空串。 |
| `next_fetch_at` | 到期时间。「更新」和「全部更新」只把它改成现在，不在请求里抓。 |
| `prompt_summary`、`prompt_translate` | 覆盖全局 prompt，空就用全局的。 |
| `auto_summary`、`auto_translate` | 按源开关，默认关。没有全局开关。 |
| `translate_titles` | 开关，默认 `0`（关）。开着时这个源的新条目的标题排进 AI 队列，成批翻成目标语言，译文存在条目上，见[「AI 摘要和翻译」](ai.md#ai-摘要和翻译)的「标题翻译」。 |
| `mute_keywords` | 按行分隔的屏蔽词，见[「屏蔽词」](api.md#屏蔽词)。全局的屏蔽词另存在设置 `mute_keywords`，对所有源生效。 |
| `paused` | 暂停的源不抓，也不能标到期。 |
| `keep_days` | 这个源自己的保留期限，单位天：`0` 跟随全局的 `retention_days`（默认），`-1` 永久保留，`1` 到 3650 是天数。其它值（小于 -1，大于 3650）不接受，见[「保留期限」](#保留期限)。 |
| `pace_sec` | 这个源的节奏：条目在「全部」和「未读」里停留多久，单位秒。`0` 是关（默认，条目一直在），否则是 3600 到 2592000（30 天）的整数，见[「节奏」](timeline.md#节奏)。 |
| `hide_from_all` | 开关，默认 `0`（关）。开着时这个源的条目不进「全部」和所在形态的时间线，只在点进这个源时看到，见[「不在全部里出现」](timeline.md#不在全部里出现)。 |
| `daily_cap` | 每天最多几条，默认 `0`（关）。大于 0 时，这个源一天里超过这个数的新条目在「全部」和「未读」里折成一行，见[「每日上限」](timeline.md#每日上限)。 |
| `folder_id` | 这个源所在的文件夹，见[「文件夹」](#文件夹)；`NULL` 是不在任何文件夹里（默认）。引用 `folders(id)`，`ON DELETE SET NULL`。 |
| `noisy_dismissed` | 用户在订阅健康里忽略「条目很多、很少读」的建议时，源当时每天写入的条数（四舍五入的整数）；`0` 是没有忽略过。见[「订阅健康」](#订阅健康)。 |
| `extract_selector`、`extract_referer`、`extract_rewrites` | 这个源自己的正文抽取规则，默认都是空串（不用规则）：一个 CSS 选择器，抽取时要发的 `Referer`，以及抽取前改写条目链接的规则（按行分隔）。语法、上限和失败时的行为见[「正文抽取」](fetching.md#正文抽取)的「按源规则」。 |
| `fetch_user_agent`、`fetch_referer` | 这个源自己的抓取请求头，默认都是空串（不改）：抓取时发的 `User-Agent`（空串是 `Oriel/<版本>`）和 `Referer`。哪些请求用、校验和边界见[「抓取」](fetching.md#抓取)的「自定义请求头」。不是密钥，照常备份。 |
| `open_target` | 点开这个源的条目时看哪里：`follow`（默认，跟随形态：文章在阅读栏，别的形态按「当前界面」的「时间线」里的「打开条目」）、`reader`（在阅读栏里看）、`browser`（用系统浏览器打开）。见[「当前界面」](screens.md#当前界面)的「时间线」里的「点开时」。 |
| `proxy`、`proxy_user`、`proxy_password` | 这个源自己的抓取代理，默认空串（跟随全局，见[「抓取」](fetching.md#抓取)的「代理」）。`proxy` 是 `direct`（这个源直连，不走全局代理，也不认环境变量）或代理地址（`http`、`https`、`socks5`、`socks5h`，写法同设置 `fetch_proxy`）；`proxy_user`、`proxy_password` 是它的用户名和密码，和 AI 的 API key 一样只存库里，接口不下发。 |
| `websub_hub`、`websub_topic` | 订阅里声明的 WebSub hub 和主题（`rel="self"`），没有为空串，见[「WebSub 推送」](fetching.md#websub-推送)。 |
| `websub_key`、`websub_secret` | 这个源的回调路径令牌和签名密钥，各自随机生成，只存库里，接口不下发。 |
| `websub_state`、`websub_expires_at`、`websub_requested_at`、`websub_base`、`websub_next_at`、`websub_failures`、`websub_error` | 订阅状态：`''`（没订）、`pending`（等 hub 验证）、`active`（租约有效到 `websub_expires_at`）；最近一次请求的时间和当时用的公开地址；下一次动作（订阅或续订）的时间；连续失败次数和最近的原因。 |

`url` 和 `rsshub_path` 合起来唯一，同一订阅不能加两次。比较订阅地址时先规范化，规则只在服务端（`internal/store/duplicate.go`）有一份，添加、订阅发现、OPML 导入和导入其他阅读器都用它：协议不分（`http` 和 `https` 一样）、主机名小写（国际化域名按其 ASCII 形式比较）并去掉开头的 `www.`、去掉默认端口（http 的 80、https 的 443）和 `#` 片段、路径末尾的 `/` 忽略（空路径等于 `/`）、跟踪参数（`utm_*`、`fbclid`、`gclid` 等，同「同一篇文章只显示一次」）去掉、其余查询参数按名字排序，所以 `https://a/feed` 和 `http://www.A:80/feed/?utm_source=x` 算同一个订阅；路径大小写（`%2F` 与 `/` 也不同）、别的查询参数、非默认端口、别的子域名、不同的用户名或密码不同则不同；地址里的用户名和密码只参与比较，不写进日志，也不在响应里回显。同一个上游也算同一个订阅：RSSHub 路由（`rsshub_path`）和落在某个 RSSHub 实例上的普通地址（`https://<实例>/github/issue/a/b` 对路由 `/github/issue/a/b`，实例是设置里的，或某个源上次成功抓取用过的，实例地址带路径时只认这个路径下的）互为重复，不分哪个先加；YouTube 的路由 `/youtube/channel/<id>`、`/youtube/playlist/<id>` 和对应的 `https://www.youtube.com/feeds/videos.xml?channel_id=<id>`、`?playlist_id=<id>` 也是同一个。其余路由没有这样的对应，不比较。库里仍存用户给的原样地址，不改写。数据库的唯一索引只拦完全相同的写法，规范化比较在添加时做（订阅数不大，不加索引）：服务端每个请求把全部订阅的比较键读一次放进内存，订阅发现和 OPML 导入、导入其他阅读器都只读这一次，不会每条订阅查一次库。

### 文件夹

用文件夹把订阅归拢起来。表 `folders`：`id`，`name`（去掉首尾空白后 1 到 60 个字符，不分大小写唯一），`created_at`。

- 一个订阅最多在一个文件夹里，文件夹不嵌套；没有文件夹的订阅单独列出。文件夹是整理订阅用的，不是第五种形态：形态仍是订阅自己的，一个文件夹里可以有各种形态的订阅。
- 删除文件夹时里面的订阅不删，变成没有文件夹（`folder_id` 置空）；订阅和它的条目、设置、阅读状态都不动。文件夹本身不影响抓取、保留和阅读状态。
- 软删除的订阅（见[「删除订阅与撤销」](#删除订阅与撤销)）保留它的 `folder_id`，撤销时回到原来的文件夹；它所在的文件夹在窗口内被删掉，撤销后它没有文件夹。
- 文件夹没有自己的开关。「不在全部里出现」「节奏」这些仍是订阅自己的设置，文件夹时间线遵守它们，见下面「文件夹时间线」。

### 订阅健康

把没在认真订阅的源挑出来，让用户自己决定暂停还是退订。只看没暂停的源（暂停是用户已经做过的决定），每个源最多落在一种状态里，从重到轻依次判断（已失效、总在失败、已搬家、条目太多、很少读）：

| 状态 | 原因 `cause` | 条件 |
|---|---|---|
| 已失效 `dead` | `failing`：一直失败 | 连续失败至少 3 次，且距离上次成功抓取（从没成功过则距离订阅时间）已满 30 天。 |
| 已失效 `dead` | `silent`：没有新内容 | 距离最新一条条目的写入时间（`created_at`；源里还没有条目则距离订阅时间）已满 90 天。两个原因都成立时记为 `failing`。 |
| 总在失败 `failing` | 无 | 连续失败至少 3 次，还没到失效。 |
| 已搬家 `moved` | 无 | 有等着用户决定的地址建议（`moved_url` 不为空，见[「抓取」](fetching.md#抓取)的「永久重定向」）。不是问题，是一个能一键办完的整理：这一行的动作是「更新地址」和「忽略」，不是「暂停」和「退订…」。 |
| 条目太多 `noisy` | 无 | 没设「每日上限」，订阅已满 7 天；设 `d` 为订阅已过的整天数（最多 30），近 30 天写入的条目至少 `20 × d` 条（平均每天至少 20 条），其中已读的不超过 5%；并且没有被忽略，或忽略后每天的条数已涨到忽略时的 2 倍以上（见下面）。这一行的动作是「放慢」「暂停」和「忽略」，见下。 |
| 很少读 `rarelyRead` | 无 | 订阅已满 30 天，近 30 天写入的条目至少 10 条，其中已读的不到 10%；没有被忽略（见下面）。 |

- 天数按 24 小时算，`days` 是这个原因已经持续了多少整天：失败和没有新内容是上面各自的间隔，很少读是 30（统计窗口）。
- 没有新内容按条目写入时间 `created_at` 算，不按发布时间：时间线本来就按写入时间排，旧条目被订阅方改日期或补发不应让一个死源显得活着。
- 订阅不满天数的源不会进入对应的状态（失败和没有新内容以订阅时间为起点，很少读要求订阅已满 30 天），所以刚加的源不会一上来就被点名。
- 「很少读」只看 `is_read`，批量标为已读（「全部标为已读」「标记更早的」）也算已读：库里不区分批量和手点。这样偏向少报，一个常常一键清空的用户的源不会被说成很少读；代价只是列表变短，而这个视图不会自动改任何东西。
- 近 30 天的条数不含被屏蔽词隐藏的条目（收藏的除外，和时间线一样）：看不到的条目没法读，不该拉低已读比例。「没有新内容」不受屏蔽词影响。
- 「条目太多」是给吵得几乎没人读的源的建议，比「很少读」更早、更具体：订阅满 7 天就能判断，它的数据窗口是订阅已过的天数（最多 30 天），所以一个新订阅、每天 40 条、一条没读的源，一周后就会被点名。每天的条数 `perDay` 是近窗口内写入条数除以 `d`，四舍五入；原因文字带着它和已读的比例：「每天 40 条，你读了 3%」（比例向下取整，一条没读是 0%）。同时满足「条目太多」和「很少读」的源记为「条目太多」。设了「每日上限」的源不会是「条目太多」（用户已经处理了），仍可能是「很少读」。
- 建议只提醒，不自动改：「放慢」发 `PATCH` 把 `paceSec` 设成 10800（快讯，见[「节奏」](timeline.md#节奏)），已经是这个值或更短的节奏时不显示这个按钮；「暂停」同上面的暂停。两个动作都复用已有的设置，没有新的状态。
- 「忽略」发 `POST /api/sources/{id}/noisy/dismiss`：服务端按现在的数据算出这个源每天的条数，存进 `noisy_dismissed`，返回 `204`；这个源现在不是「条目太多」（数据变了、已经设了上限或暂停了）时 409 `not_noisy`，什么都不改。被忽略的源不再出现在「条目太多」，也不会落到「很少读」；直到它每天的条数涨到忽略时的 2 倍或更多，才会再次被点名（忽略时存的条数不会自己更新，再次点名后可以再忽略一次，换成新的条数）。只看条数，读得多少不算变化。
- 数值是常量，不做成设置。要改（比如把 90 天改成 6 个月）改一个常量即可。
- 在存储里算，除了「忽略」存的那一列不加表和索引：一次查询取没暂停的源，一次按源分组取最新条目时间（走 `entries_source_timeline` 覆盖索引），一次按源分组统计近 30 天的条目数、已读数和收藏数（走 `entries_timeline` 范围扫描），在内存里合并，不对每个源再做子查询。

### 抓取记录

表 `fetch_log`：每次抓取的结果留一行，给「活动」界面看每个源最近抓得怎么样。和订阅健康不同，它不下判断，只记事实。

- 一行一次抓取：源（`source_id`，删源时一起删）、结束时刻 `at`（毫秒）、耗时 `duration_ms`（从开始抓到有结果，含 RSSHub 换实例的时间）、是否成功 `ok`、最后一次收到的 HTTP 状态码 `status`（没收到响应为 0；304 记 304，算成功）、这次新增的条目数 `new_entries`、失败原因 `error`（成功为空串，和 `last_error` 同一段文字，最长 300 个字符，超出截断）。
- 记的是「有了结果」的抓取，和 `FetchSuccess`、`FetchFailure` 记账的时机一致。什么都没试的（主机忙、实例在冷却，见[「抓取」](fetching.md#抓取)）和因关闭进程而取消的不记。
- 每个源只留最近 10 次（常量 `FetchLogKeep`），新的一行和裁掉更旧的行在同一个事务里，所以库不会随时间变大：上限是源数乘 10 行。保留条数不是设置，也不受 `retention_days` 影响。
- 索引 `(source_id, id DESC)`。读的时候一次查询取全部记录，在内存里按源分组，不对每个源再做子查询。

### RSSHub 实例健康

设置里每个 RSSHub 实例显示它最近答得怎么样，让用户判断该把哪个排在前面、该删哪个。和抓取记录一样只记事实，不下判断：不给实例打分，不自动调整顺序，也没有额外的探测请求。

- **统计什么。** 抓取一个 RSSHub 路由时，每向一个实例发出的一次请求算一次「请求」，包括换实例时先失败的那次，也包括只有一个实例的情况。「答上来」的判断同「抓取」里的实例失败：收到了响应、又不是 5xx 和 429，就是答上来（含 304，以及 404、解析失败、响应过大这类路由的问题）；无响应（连不上、超时、读到一半断开）、5xx、429 是没答上来。因关闭进程而取消的不算；在冷却里被跳过的、主机忙而没发出的也不算，它们没有请求。完整地址的订阅（不经实例）不算。
- **窗口。** 每个实例留最近 50 次请求（常量 `InstanceHealthKeep`），读的时候再丢掉超过 7 天（常量 `InstanceHealthDays`）的。两个条件都要满足：很久没用的实例不会拿几天前的结果当现状，常用的实例也不会被很旧的请求拖住。
- **算法。** `requests` 是窗口里的请求数。成功率 `successRate` 是答上来的次数除以 `requests`，范围 0 到 1，`requests` 为 0 时没有（`null`）。中位延迟 `medianMs` 是答上来的那些请求的耗时的中位数，偶数个时取中间两个的平均，取整到毫秒，没有答上来的请求时没有（`null`）。耗时从发出请求到收到响应头，不含读取响应体、解析和写库，所以大订阅源和慢的写库不会让实例显得慢。没答上来的请求不进延迟：超时的耗时是「等了多久」，不是实例的速度。
- **冷却。** 实例在冷却中时带 `coolingUntil`（冷却结束的毫秒时间戳，不在冷却中为 `null`）。只有一个实例时不设冷却，所以始终是 `null`。冷却的原因不给界面：失败原因已经写在订阅的 `last_error` 里。
- **存在哪里。** 只在服务端内存里，随抓取更新，重启服务端后清空，不加迁移、不写库。不存库是有意的：现有的抓取记录（`fetch_log`）每个源只留 10 次，也不记是哪个实例答的，换实例时先失败的那次也不在里面，用它算不出实例的成功率；为此改它的列和保留规则，换来的只是重启后不丢一个只看最近的数字，不值得。代价是重启后要抓几次才有数据，界面里写明这一点（见[「设置界面」](screens.md#设置界面)的「抓取」）。内存是有界的：每个实例最多 50 条，设置里最多 5 个实例，读的时候丢掉不在设置里的实例的统计，所以去掉又加回来的实例从空开始。
- **接口。** `GET /api/rsshub/health` 按设置 `rsshub_base_url` 的列表和顺序返回，要会话（设了口令时），见[「活动和存储接口」](api.md#活动和存储接口)。数据取自抓取循环，不经数据库。

### 条目

源里的一条内容，按 `(source_id, guid)` 去重；没有 guid 时用规范化后的条目 URL。删源时条目一起删。

订阅换了 guid 但链接没变时仍是同一条：抓到 guid 库里没有的条目时，若同一个源里恰好有一条已有条目的规范化链接（小写协议和主机名、去掉 `#` 片段、跟踪参数和路径末尾的 `/`，跟踪参数见[「阅读器」](screens.md#阅读器)的「链接里的跟踪参数」）与它相同，就当作那一条，更新内容并改存新 guid，已读、收藏和抓好的全文都留着，不再新增。链接为空、本源里有多条已有条目用同一链接、这次抓到的条目里有多条用同一链接（比如全都指向首页），或者那条已有条目的 guid 这次还在订阅里，都不合并，按新条目处理。这一步只在同一个源里认条目；不同源的同一篇文章在库里仍是各自的条目，时间线上怎么只显示一次见下面的「同一篇文章只显示一次」。

| 字段 | 说明 |
|---|---|
| `guid`、`title`、`url`、`author`、`published_at` | 来自订阅。`published_at` 只用来展示，会被重新发布覆盖。 |
| `rss_summary`、`rss_content_html` | 订阅里的摘要和正文。 |
| `extracted_html`、`extract_status`、`extract_attempts`、`next_extract_at` | 抽取的正文。状态 `pending` → `ok` / `failed`；非文章形态（含社区）和关了 `full_text` 的源为 `skipped`。`next_extract_at` 是失败后最早再试的时刻（毫秒），可为空：不再自动重试。 |
| `copy_status`、`copy_attempts`、`next_copy_at` | 收藏的本地副本（见[「收藏的本地副本」](#收藏的本地副本)）。状态 `none`（没收藏）→ `pending` → `ok` / `failed`；`next_copy_at` 是失败后最早再试的时刻（毫秒），可为空：不再自动重试。图片副本另存在表 `entry_image_copies`。 |
| `kind` | 所属源的 `kind` 的副本，只为让「按形态」和「未读」的时间线走索引；数据库触发器在新条目写入和源改形态时同步，不由接口读写。 |
| `thumbnail_url`、`duration_sec`、`platform` | 视频和社交的展示信息。 |
| `language` | 条目文字的语言，BCP 47 码：ISO 639-1 的两个字母（`en`、`de`、`ja`……），中文分 `zh-Hans` 和 `zh-Hant`，没有两字母码的语言用三字母码。可为空（`NULL`）：文字太短或检测没有把握时不写，不猜。见[「语言检测」](#语言检测)。 |
| `images` | JSON 数组，每项 `{ "url", "width"?, "height"? }`，没有图为 `[]`。 |
| `is_read`、`read_at`、`starred` | 阅读状态。收藏的条目不被保留期限清理。未读的条目有一个按源的部分索引，`GET /api/sources` 的 `unreadCount` 只读各源自己的未读行；没设屏蔽词的源不逐条判断屏蔽。 |
| `link_key` | 跨源认同一篇文章用的链接指纹，由 `url`（或 guid）算出，空串表示不参与合并；服务端维护，不由接口读写。见[「同一篇文章只显示一次」](#同一篇文章只显示一次)。 |
| `search_text` | 抽取正文的纯文本，进全文索引。 |
| `reading_sec` | 估计要花的时间，单位秒，服务端算好存下。可为空（`NULL`）：没有可估的内容，或还没算。见[「阅读时间」](#阅读时间)。 |
| `read_progress` | 读到文章的哪里，0 到 1 的小数：滚过的距离 ÷ 可滚动的总距离（内容高减视口高）。可为空（`NULL`）：从没滚动过。见[「当前界面」](screens.md#当前界面)的「阅读器」里的「阅读位置」。 |
| `translated_title`、`title_tr_status`、`title_tr_attempts`、`title_tr_at` | 标题翻译（见[「AI 摘要和翻译」](ai.md#ai-摘要和翻译)的「标题翻译」）：`translated_title` 是译文，没有为空串；`title_tr_status` 是 `''`（没排队，或不需要翻）、`pending`（排队中）、`ok`、`failed`；`title_tr_attempts` 是单条重试了几次，`title_tr_at` 是最近一次试的时刻（毫秒）。是派生内容，不改条目的 `updated_at`；`translated_title` 进「检索语法」的匹配，不进全文索引。有一个只含 `pending` 和 `failed` 行的索引（后台队列用）和一个只含有译文的条目的索引（检索用）。 |
| `remind_at` | 稍后提醒我的时间，Unix 毫秒。可为空（`NULL`）：没有提醒。有值的条目是已读的，到点后变回未读并排到最上面。有一个只含有值行的索引。见[「稍后提醒我」](api.md#稍后提醒我)。 |
| `folded` | `1` 表示这条因为源的「每日上限」被折叠：只在「全部」「未读」和形态时间线里折成一行，是服务端维护的状态，不由接口读写。默认 `0`。只有未读且未收藏的条目会是 `1`：数据库触发器在条目被标为已读或收藏时把它清成 `0`。有一个只含 `folded = 1` 行的索引。见[「每日上限」](timeline.md#每日上限)。 |

时间线按 `created_at, id` 排序和分页，不用 `published_at`。

### 条目的修订

文章更新后，阅读器标出改了什么。每个条目只留上一个版本，表 `entry_revisions`：

| 列 | 含义 |
|---|---|
| `entry_id` | 主键，指向 `entries(id)`，`ON DELETE CASCADE` |
| `title` | 上一个版本的标题 |
| `summary` | 上一个版本的订阅摘要（`rss_summary`） |
| `content_html` | 上一个版本的订阅正文（`rss_content_html`） |
| `fetched_at` | 上一个版本抓到的时间，也就是更新之前条目的 `updated_at` |
| `replaced_at` | 这次更新抓到的时间，就是界面上写的更新时间 |

- 什么算改了：标题，或正文（订阅正文，没有就用摘要）的文字，在把空白归一（连续空白合成一个）并去掉跟踪图片（`internal/tracker` 认得的）之后和旧版本不一样。只有时间戳、空白、跟踪图片、标记的变化不算，不存修订。比较的是订阅里带的内容，不是抽取的全文（`extracted_html`）。
- 存的时机：抓取写入已有条目时，在覆盖之前，同一个事务里。已经有修订的条目再次更新，旧的修订被替换，只留最近一次更新之前的版本。
- 已读的条目被更新后仍是已读，不变回未读；时间线和阅读器标明它已更新（见下面的 `revisedAt`）。
- 保留期限清理条目时，修订随条目一起删（外键级联）；收藏的条目连同它的修订一起保留。
- 接口：`GET /api/entries/{id}/revision`，返回 `{ "fetchedAt": 毫秒, "updatedAt": 毫秒, "previous": { "title", "paragraphs": [...] }, "current": { "title", "paragraphs": [...] } }`。`paragraphs` 是纯文本的段落（块级元素和换行分段，空白归一，跟踪图片不算）。条目不存在，或没有修订，404 `not_found`；要会话。逐段的差异由客户端在后台算。
- 条目的 JSON 在有修订时多一个 `revisedAt`（`replaced_at`，Unix 毫秒），没有时不出现。

### 同一篇文章只显示一次

几个源常常带同一篇文章（同一篇博客被聚合站、专栏和本人的订阅各转一遍）。设置 `groupSameLink` 开着（默认开）时，时间线把链接相同的条目合成一行；关掉时每个源的每一条各占一行。合并只发生在读的时候：库里仍是一源一条、一条一行，抓取、去重、保留期限、收藏的本地副本都不认「组」，没有组表，也没有谁被删掉。

**链接怎么算相同。** 每条条目存一个 `link_key`（有一个按 `link_key, created_at, id` 的部分索引，只含非空的），抓取写入和更新条目时同步重算。两条条目的 `link_key` 相同才算同一篇。算法比「订阅换了 guid」用的同源比较（见上）更宽松，因为跨源要认出的是同一个页面的不同写法：

- 取条目链接；链接为空而 guid 是 http 或 https 地址时用 guid。别的 guid 不认：它们只在各自的订阅里有意义，跨源会撞。
- 协议不比（`http` 和 `https` 相同）；主机名转小写，去掉开头的 `www.` 和默认端口；去掉 `#` 片段和路径末尾的 `/`；路径的大小写不动。
- 查询串里去掉追踪参数（清单见[「阅读器」](screens.md#阅读器)的「链接里的跟踪参数」，打开、复制和导出用的是同一份）；剩下的参数按名字排序，别的参数都留着（`?id=1` 和 `?id=2` 是两篇）。
- 链接为空、解析不了，或者去掉上面这些之后只剩主机名（首页，路径空，也没有查询串）时 `link_key` 为空串，不参与合并：好些订阅的所有条目都指向首页。
- 标题、正文、作者不参与比较；链接不同就是不同的文章，「讲同一件事」的不合并。

**主条目。** 一组里排在时间线上的那一条：组里可见的成员中最早到达的，也就是 `(created_at, id)` 最小的。可见是指没被源的屏蔽词隐藏、源没被删（收藏的不被屏蔽，同「屏蔽词」），并且不是节奏已到期的未读条目（见[「节奏」](timeline.md#节奏)）。选最早到达的，是因为这样一行在时间线上的位置和游标不会因为后来又有源转了同一篇而变：新成员只会排在主条目之后，不会把已读过的行挤到别处或重新顶到最上面。主条目所在的源就是行上显示的源，其余成员是「另见」。各源自己的屏蔽词照常按成员判断：被屏蔽的成员不算成员，不出现在「另见」里，也不当主条目。

**已读和收藏。** 组整体一个状态：
- 组里有任何一个可见成员已读，这一组就算已读；有任何一个成员收藏，这一组就算收藏。`isRead`、`starred` 在行上就是这个汇总值。因此后来才抓到的又一份转载不会把已读的行重新变成未读。
- 把一条标成已读、收藏或取消收藏（`PATCH`），改的是组里所有可见成员，不管点的是主条目还是「另见」里的某一份；标成未读把所有成员都改回未读。所以不会出现「行显示已读，点开另一份却是未读」。
- 「全部已读」及其变体标的是时间线上那些行，行所在的整组一起标。
- `readProgress` 是阅读器里的滚动位置，不分组，各条目自己存。

**筛选。** 「未读」只留下组里没有任何成员已读的行，「收藏」留下组里有任何成员收藏的行；形态和时间范围按主条目判断；排序、游标按主条目。时间范围看主条目的 `created_at`：一篇文章最早到达的那份在范围之前，后来又有源转了它，也不算范围内的新内容（已经见过的不算新）。按单个订阅看（`source`）时不合并：用户要看的就是这个订阅里有什么，行上的已读、收藏也是这一条自己的。检索（`q`）也不合并，结果是匹配的每一条本身。

**数量。** 各源的 `unreadCount` 数的是这个源自己的未读（见[「数据模型」](#数据模型)），所以各源数字加起来可以比时间线上的未读行多。`GET /api/sources` 另给 `unreadTotal`：时间线「未读」里的行数，一组只算一次，也就是侧栏「全部」应该显示的数；`groupSameLink` 关着时它等于所有源 `unreadCount` 之和。

**接口里的组。** 成员不止一个的条目带 `group`：`{ "by": "link", "entries": [...] }`，`entries` 是组里除这条之外的可见成员，每项 `id`、`sourceId`、`sourceTitle`、`title`、`url`、`isRead`、`starred`、`createdAt`，按 `createdAt, id` 从早到晚排。单条没有 `group` 字段。`by` 的取值是 `link`。`GET /api/entries/{id}` 对主条目和成员都带 `group`（对成员，`entries` 里有主条目）。

### 规则

用户写的规则：新条目到来时，条件都满足就自动加星标或标为已读。表 `rules` 和 `rule_sources`：

| 字段 | 说明 |
|---|---|
| `rule_sources` | 另一张表，一行一个（`rule_id`、`source_id`）：规则只管这些源；一行也没有：管所有源。删源时它那几行一起删；规则的源因此删光时，规则也一起删（不会变成管所有源的规则）。 |
| `kind` | 只管这种形态（`article`、`video`、`social`、`image`、`forum`）；空串：不限形态。 |
| `keywords` | 按行分隔的关键词，规则和「屏蔽词」同一套匹配：标题或订阅摘要里包含其中任何一个。空串：不看关键词。 |
| `exclude_keywords` | 按行分隔的「不含」词，同一套匹配：标题或订阅摘要里包含其中任何一个，规则就不命中。空串：不排除。 |
| `author` | 作者里包含这段文字（子串，不分大小写）。空串：不看作者。 |
| `star`、`mark_read` | 动作，0 或 1，至少一个为 1。 |
| `enabled` | 0 或 1，默认 1。关掉的规则保留，但不再执行。 |
| `created_at` | 创建时间，列表按它排。 |

规则的语义见[「规则」](timeline.md#规则)。全局屏蔽词不在这张表里，是设置 `mute_keywords`（见[「屏蔽词」](api.md#屏蔽词)）。

### 语言检测

抓取写入条目时，用纯 Go 的检测库（`github.com/abadojack/whatlanggo`，MIT）判断条目的语言，不联网：

- 样本是标题加上订阅里摘要或正文的纯文本，最多取前 3000 个字符。字母少于 20 个，或检测库认为不可靠（置信度不高于 0.8），语言就留空。
- 检测成中文时，数只有繁体或只有简体才用的常用字：繁体字更多为 `zh-Hant`，否则（含相等）为 `zh-Hans`。
- 文章形态抽取到全文后，用全文重新检测一次，检测出来才覆盖；检测不出来保留原值。
- 订阅内容之后变了，条目被重新写入时语言一并更新；检测不出来保留原值。语言不回填：没有语言的条目保持为空，直到内容变化而重新写入。

语言用在两处：目标语言（`aiLanguage`）和条目语言相同的条目，自动翻译不排队（摘要照常）；阅读器里这样的条目不能翻译，并写明原因（例如已经是简体中文）；阅读器按条目语言选正文的行高，语言为空时按标题和正文有没有汉字判断。语言为空的条目可以翻译。

### 阅读时间

服务端为每个条目估一个要花的时间，存在 `reading_sec`（可为空），让列表带上它。估计只用条目自己的内容，不联网，不看用户的阅读速度。

来源，按顺序取第一个适用的：

1. `duration_sec` 大于 0（视频、播客，来自 `itunes:duration`、`media:content`、JSON Feed 的 `attachments.duration_in_seconds`）：`reading_sec` 就是这个时长，不再看文字。JSON Feed 有多个附件时，使用第一个大于 0 的时长。
2. 形态是视频或图片：没有时长就为空，不拿描述文字估，因为文字不是要花时间的内容。
3. 文章、社交和社区：按文字估，文字取手头最好的一份——抽取的正文（`extract_status` 为 `ok` 时的 `search_text`）；没有就用订阅里的正文（`rss_content_html` 的纯文本）；再没有就用摘要（`rss_summary`）。只有摘要时照样估、照样显示（按摘要估的，满 1 分钟才会显示，所以很少见）；抽取还没完成时先按订阅里的内容估，抽出全文后重算。
4. 没有任何文字（去掉标签和空白后一个字都没有）：为空。

按文字估的算法：

- 数两样东西：汉字和假名（每个算一个字，不分词），以及其余文字里的词。词是连续的字母或数字，以空白和标点分开（包括韩文、拉丁、西里尔等，一律按词数）。标点、符号、空白不算。HTML 先转成纯文本，脚本、样式和计数图片不算；图片不加时间。
- 秒数 = 字数 × 60 ÷ 400 + 词数 × 60 ÷ 220。每分钟 400 个汉字或假名、220 个词，中英混排按各自的数量相加。不按条目的 `language` 区分，数字符本身就够，语言为空也一样。
- 取整：不到 60 秒的存成四舍五入的整秒数，不显示；满 60 秒的四舍五入到整分钟再存（90 秒是 2 分钟，89 秒是 1 分钟），存的值总是 60 的倍数。所以界面上的「N 分钟」就是存的数。时长（第 1 条）不取整，存原来的秒数。

什么时候算：

- 条目被写入时（新条目，或内容变了而重新写入时），按当时的内容算。
- 抽取成功写入正文时重算。抽取失败或跳过不重算。
- `reading_sec` 为空而有内容的条目：SQL 里不能分析文字，所以由服务端启动后在后台补：按 `id` 从小到大，每批 200 条，批与批之间让出时间，不挡抓取和接口；已补到哪个 `id` 记在设置里（`reading_backfill_id`），重启接着补，补完不再扫描。补完之前，这些条目没有时间，不显示。

显示：

- 满 60 秒、不是视频形态、且 `reading_sec` 来自文字的条目显示阅读时间，单位是分钟，就是 `reading_sec` ÷ 60。不到 1 分钟、为空、或来自时长的不显示。视频形态的封面已有时长，不再重复；有时长的文章（播客）也不显示这个标签，因为它不是「读」。
- 为空的条目在任何地方都不显示时间，不写 0。

不按阅读时间筛选，接口不接受 `maxMinutes`。估计的时间只用来显示。

### 时间范围

时间线可以只看最近到达的条目：「不限」（默认）、「今天」、「最近 24 小时」。它回答「我今天来了之后/这一天里来了什么」，是视图筛选，不改任何条目的状态。

- 比较的是条目进入 Oriel 的时间 `created_at`，不是发布时间 `published_at`：抓到一篇三天前发布的旧文，它今天才到，就算今天的。
- 「今天」是从客户端本地时区今天零点起；「最近 24 小时」是从现在往前 24 小时。两者都由客户端算成一个绝对的 Unix 毫秒时间戳，作为 `since` 发给服务端（见[「时间线接口」](api.md#时间线接口)），服务端只比较时间戳，不认时区，也没有「今天」的概念。客户端每次载入列表（包括换范围、重新加载、切换保留的后台刷新、每 60 秒的新条目检查）都按当时的时间重新算 `since`，所以过了午夜再刷新，「今天」就换成新的一天；一直不刷新的列表保持原样，不会自己抽走条目。
- 和「全部 / 未读 / 收藏」、形态、订阅、检索叠加，排序不变。
- 范围里没有条目时显示空状态，可以一步取消范围。
- 「全部标为已读」及其变体（把上面的、把下面的、把 N 前的标为已读、V）在范围开着时只标范围内的条目：请求带同样的 `since`，所以范围之前的未读不会被一起标掉。「当前范围有未读」按范围内的列表判断。右键订阅的「把订阅标为已读」是订阅自己的动作，不看时间范围。
- 侧栏和形态上的未读数是整个订阅或形态的未读，不随时间范围变。范围开着时，时间线标题旁的未读数不显示（它数的是整个范围，不是范围内的）。
- 记在这台设备上：范围和范围（形态或订阅）、「全部 / 未读 / 收藏」一起记在 `places` 里，按服务端分开，重启后回到（见[「当前界面」](screens.md#当前界面)的「时间线」里的「重启后的位置」）。
- 它是列表缓存键的一部分（见[「当前界面」](screens.md#当前界面)的「时间线」里的「切换保留」）：同一个范围加筛选下，换时间范围各有各的缓存列表。因为「今天」的起点随日子变，切回缓存的列表时照常先画出缓存，再按当时的 `since` 在后台重新取第一页；缓存里已落在范围外的条目（过了午夜）在合并时去掉。
- 索引：`since` 比较 `created_at`，和排序同一列；查询计划见 `internal/store` 的测试，没有出现全表扫描，所以不加迁移。

### AI 结果

一个条目的一种 AI 结果一行，任务是 `summary`（摘要）或 `translation`（翻译），按 `(entry_id, task)` 唯一。删条目时一起删。

| 字段 | 说明 |
|---|---|
| `status` | `pending`（排队或进行中）→ `ok` / `failed`。 |
| `text` | 结果，纯文本，段落之间空一行。失败时保留上一次成功的结果。 |
| `error` | 失败的错误码，见[「AI 摘要和翻译」](ai.md#ai-摘要和翻译)。 |
| `attempts` | 自动处理试过几次，满 3 次不再自动重试。只数跟这个条目有关的失败；接口本身的失败（`ai_unreachable`、`ai_unauthorized`、`ai_rate_limited`、`ai_model_not_found`，以及接口已在退避时的 `ai_timeout`）不加一，见[「自动处理」](ai.md)。 |
| `requested` | 是用户要的（`1`）还是自动排的（`0`）；用户要的先处理。 |
| `fingerprint` | 输入的指纹：模型、生效的 prompt、目标语言和送去的原文的 SHA-256。 |
| `model` | 生成结果的模型。 |
| `updated_at` | 最近一次排队或处理的时间。 |

结果是派生内容，不改条目的 `updated_at`，不进全文索引。

AI 队列每 15 秒取一次待处理的结果，走一个部分索引 `entry_ai_open`（`status, requested`，只含状态不是 `ok` 的行），所以每轮的代价跟未完成的结果数有关，不随已完成的结果数增长。

两张辅助表：

- `entry_ai_chunks`：翻译分块的缓存，一块一行，按 `(entry_id, task, key)` 唯一，`key` 是这一块的送出内容的 SHA-256（模型、生效的 prompt、目标语言和这一块的原文），`text` 是这一块的译文，`model` 是答复的模型。只存多于一块的翻译。这一条翻译成功，或者条目删除时，这些行一起删。
- `ai_usage`：自动处理每天用了多少个请求，一天一行，主键是服务端本地时间的日期（`YYYY-MM-DD`），`calls` 是当天自动处理已发出的请求数（见[「AI 摘要和翻译」](ai.md#ai-摘要和翻译)的「发送与费用」）。用户自己点的请求不记在这里。

### 设置和会话

设置是键值表。API key 存在这里，接口不下发，只回「已配置 / 未配置」。抓取代理（`fetch_proxy`，代理地址；`fetch_proxy_user`、`fetch_proxy_password`，它的用户名和密码）同样存在这里，用户名和密码和 API key 一样只写不下发。

会话一行一台设备：token 的 SHA-256、User-Agent、用户给的名字（空着就从 User-Agent 推出）、创建时间、最近使用时间。不存 token 原文。

## 存储

- SQLite，一个文件 `oriel.sqlite`，WAL，开外键。驱动是纯 Go 的 `modernc.org/sqlite`（见 [ADR 0003](../adr/0003-pure-go-sqlite.md)）。
- 写事务一开始就取写锁（`_txlock=immediate`），并发的写互相等待（`busy_timeout` 5 秒），不会报 `database is locked`，健康的订阅源也不会因此记一次抓取失败。
- 全文检索 FTS5，分词 trigram，列为标题、RSS 摘要、`search_text`。由触发器和条目表同步。
- 迁移是内嵌的 SQL 文件，按 `PRAGMA user_version` 逐个执行，每个一个事务。只加新迁移，不改已发布的。
- 迁移前的副本：打开一个已有的库时，如果有还没执行的迁移，先用 `VACUUM INTO` 在数据库旁边写一份一致的副本 `oriel.sqlite.pre-migrate`（和数据库一样只有当前用户可读写，里面也有会话和 API key），再执行迁移。只留最近一份：新副本先写进 `.oriel-tmp-*` 临时目录，写完再改名盖掉旧的，所以写副本失败时旧副本原样还在。新建的库（`user_version` 为 0）、已经是最新的库都不写副本，也不动已有的副本。写副本失败（磁盘满、目录不可写……）时打开数据库就失败，不带着没有副本的风险去迁移，数据库本身没动；成功时写一条日志，带副本的文件和迁移前后的版本。更新后发现不对劲，或者要退回旧版本（旧版本打不开新版本迁移过的库，见 `ErrSchemaNewer`）：先完全退出 Oriel，装回旧版本，删掉 `oriel.sqlite-wal` 和 `oriel.sqlite-shm`（还在的话），再把 `oriel.sqlite.pre-migrate` 复制成 `oriel.sqlite`。副本里是迁移前的数据，更新之后才有的改动不在其中。副本不再需要时可以直接删除，也可以在设置的「活动与存储」里删（见下）。
- 同一个数据目录只能有一个 Oriel 进程：打开数据库时对旁边的 `oriel.sqlite.lock` 加系统文件锁，第二个进程直接报错。进程崩溃时系统会释放锁。
- 数据库文件只有当前用户可读写（`0600`），里面有会话和 API key。
- 压缩数据库（`VACUUM`）由用户在「活动与存储」里手动触发，见[「活动和存储接口」](api.md#活动和存储接口)。
- 备份、恢复的临时文件放在数据目录的 `.oriel-tmp-*` 子目录里，用完就删；进程崩溃留下的，下次打开数据库时清掉。
- 数据目录里还有代理图片的缓存 `image-cache/`（见[「图片代理」](api.md#图片代理)），是可再生的，删掉不影响数据。
- 收藏条目的图片副本存在数据库里（表 `entry_image_copies`，见[「收藏的本地副本」](#收藏的本地副本)），所以对数据库做快照（备份）时副本一并带上，不用另外备份；它们占数据库的空间，在「活动与存储」里单独列出。

## 删除订阅与撤销

删除一个订阅可以撤销。

- `DELETE /api/sources/{id}` 只是在源上写 `deleted_at`（毫秒时间戳），不删任何行。带 `deleted_at` 的源和它的条目马上从所有地方消失：源列表、单个源、条目列表、计数、搜索、收藏、全部标为已读、订阅健康、活动、OPML 导出、导入时的地址匹配都当它不存在；抓取循环、正文抽取、AI 队列和 WebSub（订阅、续约、回调回 404）都不再碰它。
- 撤销窗口是 30 秒，由服务端算（`store.DeleteUndoWindow`）。界面的撤销提示约 8 秒，服务端多留余量，免得点撤销时刚好过期。窗口内 `POST /api/sources/{id}/restore` 清掉 `deleted_at`，源带着条目、已读和收藏状态、全部设置回来。
- 真正删除：每小时一次的清理循环（见[「保留期限」](#保留期限)）顺带删掉 `deleted_at` 早于窗口的源，条目随外键一起删；这之前它们只是藏着。过了窗口 `restore` 一律是 404，不管清理有没有跑到。**收藏的条目也一起删**：条目必须属于某个源，没有地方留；所以删除前的确认写明收藏的条目会一起删掉，撤销只管窗口内。确认默认是取消，回车不会删除；Esc 或点确认框外也是取消。
- 窗口内用同一个地址再添加：先把那个已删除的源真正删掉（连条目），再建新的，和全新添加一样，不报「已存在」。
- `deleted_at` 在库里，服务端重启不影响窗口。

## 保留期限

设置 `retention_days`，单位天：`0` 或不设是永久（默认），最大 3650，不是整数的值按永久处理。

- 清理有自己的循环（不占抓取线程），每小时最多清理一次：删除未收藏且过期的条目，已读未读无关。过期按发布时间算，没有发布时间按写入时间。
- 清理分批删除：先一次查出过期且未收藏的条目 id，再按 id 每批最多 500 条删除，每批一个事务（删除时再核对一次未收藏和过期，中途被收藏的条目不会被删），批与批之间放开写锁，其它写入可以插进来，所以保留期限改短或久未清理的大库不会长时间卡住所有写入。中途失败或被取消时，已删的批次保留，下一轮继续。
- 每个源可以有自己的 `keep_days`，覆盖全局值：`0` 跟随 `retention_days`，`-1` 永久保留，`1` 到 3650 是这个源自己的天数，可以比全局短也可以比全局长。全局是永久时，只有设了自己期限的源会被清理，所以清理循环在全局永久时也照常跑。收藏的条目在任何期限下都保留。
- 抓取时，发布时间早于保留期限（这个源自己的，没设就是全局的）的新条目直接跳过。否则订阅里还留着的旧条目会在清理后被当成新条目抓回来，以未读身份出现在时间线最上面，一小时后又被删掉，如此反复。已经在库里的条目不受影响，等清理删除。

- 条目的修订随条目一起删（见[「条目的修订」](#条目的修订)）。
- 抓取记录有自己的上限（每源 10 次，见[「抓取记录」](#抓取记录)），不看保留期限。

### 数据库维护

清理只是释放页面，文件不会自己变小，所以 Oriel 在这些时候做维护：

- 启动、迁移完成后，以及正常退出时，运行 `PRAGMA optimize`，让查询计划用上新的统计信息；正常退出时还把预写日志（WAL）合并回数据库文件并截断。这些步骤很快，失败只记日志，不影响启动和退出；退出时它们发生在请求都结束、后台工作都停下之后、关库之前，用退出总期限里剩下的时间，最多 3 秒，到时放弃。
- 一次清理删除了至少 200 条条目（常量 `MaintainAfter`）之后，在清理循环里把空闲页还给磁盘：`auto_vacuum` 是 `INCREMENTAL` 的库，用 `PRAGMA incremental_vacuum` 每次最多归还 500 页，每一步是一个很短的写事务，写入和抓取不会被长时间挡住；归还完再截断预写日志，并运行 `PRAGMA optimize`。
- 清掉已删除订阅（撤销期满，连带删除它们的全部条目）时同样处理，按连带删除的条目数算。清理被打断（关闭进程取消了上下文，即退出）时不做这一步，留给之后的清理。
- 新建的库从一开始就是 `auto_vacuum = INCREMENTAL`。模式不是 `INCREMENTAL` 的库要改模式，必须做一次完整的 `VACUUM`，而这会重写整个文件、期间持有写锁：所以后台的清理循环从不自动做它。这样的库上，大清理之后只截断预写日志并运行 `PRAGMA optimize`，文件不会变小；用户在「活动与存储」里手动压缩一次（`VACUUM`，见[「活动和存储接口」](api.md#活动和存储接口)）后，库就转成增量模式，之后的大清理都会增量归还空闲页。手动压缩需要的临时空间约等于数据库大小，磁盘不够时它失败，原库不受影响。后台维护和手动压缩共用同一个「正在压缩」状态，同一时刻只跑一个。

## 删除所有已读条目

在「活动与存储」里可以一次删掉服务端上的已读条目，连到这个服务端的每台设备都一样，不能撤销。接口见[「活动和存储接口」](api.md#活动和存储接口)。

- 删已读且未收藏的条目；未读的和收藏的都留着。在撤销窗口里的已删除订阅不动，撤销后它和删除时一样。
- 修订、AI 结果随条目一起删（外键级联）。收藏的条目不在其中，所以收藏的本地副本不受影响。
- 分批删除，和保留期限清理一样：先查出 id，每批最多 500 条、一个事务，删除时再核对一次规则，中途被收藏或标为未读的条目不会被删。中途失败或请求结束时，已删的批次保留，再删一次就接着删。删完后按[「数据库维护」](#数据库维护)的规则归还磁盘空间。
- 订阅里还带着的条目不会以未读身份回来：删除时按 `(source_id, guid)` 记在 `removed_entries` 里，抓取遇到记录里的 guid 就跳过，并刷新 `seen_at`。订阅连续 30 天（常量 `RemovedKeep`）不再带它，清理循环就忘掉这条记录。删除订阅时记录一起删。
- 保留期限清理不写这个记录：它靠抓取时跳过过期条目，见[「保留期限」](#保留期限)。

## 收藏的本地副本

收藏的条目是用户要留下的东西，不该因为原站改版、删文或图床失效而残缺。收藏一条时，Oriel 把它的图片和全文留在本地；条目在副本还没好之前照常显示。

存什么：

- **全文**：收藏的文章条目要有抽取好的全文（见[「正文抽取」](fetching.md#正文抽取)，走同样的 `guardedClient`，不换普通 `http.Client`）。源关了 `full_text`、条目是 `skipped` 时，收藏把它改回 `pending`。收藏时若全文抽取已失败（`extract_status` 为 `failed`），把它重置为待抽取并清零重试次数，让它再试一轮；抽取成功后的 `extracted_html` 重新抓取订阅时本来就不会被覆盖，所以一次抓取不会让收藏条目丢掉全文。全文没好之前（文章的 `extract_status` 为 `pending`）不开始复制图片，因为图片地址要从全文里取。
- **图片**：缩略图、订阅里列出的图片，以及全文和订阅正文里的 `img`（含 `data-src`），相对地址按条目链接补全，只留 http 和 https。已知的跟踪图片地址、宽或高不超过 2 像素的图、隐藏的图，和阅读界面一样不算正文，不复制（判断在 `internal/tracker` 里，阅读界面、图片代理和副本共用）。去重后按上面的顺序最多取 30 张，多的仍是指向原站的链接。
- 每张图经「图片代理」同一个取图代码（`internal/fetch/images.go`）下载：只连公网地址、不带 `Referer`、超时 25 秒、最大 8 MiB、按内容判断类型、只放行 PNG、JPEG、GIF、WebP 和 BMP。超过大小或类型不对的图直接跳过，不影响其余的图。
- 副本存在表 `entry_image_copies`：`(entry_id, url)` 唯一，存内容类型和图片字节，`entry_id` 外键 `ON DELETE CASCADE`。同一张图出现在两条收藏里各存一份。

队列和重试：

- 复制在服务端自己的后台循环里跑（和抽取、AI 各自独立），每 5 秒看一次，每次最多处理 3 条收藏的条目，一条里的图一张接一张取。收藏（`starred` 由 0 变 1，包括导入时直接收藏的条目）由数据库触发器把 `copy_status` 置为 `pending` 并清零重试次数，所以不论从哪条路径收藏都会入队，接口不必另外记。
- 永远取不到的图（跟踪地址、被拦的地址、超过大小、类型不对、404 之类不会好的状态码）跳过且不再试。可能以后会好的（连不上、超时、408/425/429/5xx）让这一次复制记为 `failed`，已经存下的图留着，下次只补缺的。失败后按 1 分钟、5 分钟、30 分钟、2 小时、6 小时退避重试（`next_copy_at`），第 6 次仍有可能好的失败后不再自动重试（`next_copy_at` 为空），再次收藏时重新开始。全部图都处理完（存下或永久跳过）则 `copy_status` 为 `ok`。
- 已删除（等待撤销）的源的条目不复制。关闭服务端时正在进行的一次不计入重试次数。

使用：

- `GET /api/image` 对一个地址先看有没有收藏条目存下的副本，有就直接返回（响应头同图片代理），原图已经失效也能显示；没有才走图片代理的取图和缓存。跟踪地址仍先被拒绝。副本按地址查，不看是哪条条目。客户端只请求 `/api/image`。

移除：

- 取消收藏（`starred` 由 1 变 0）时，数据库触发器删掉这条的所有副本，`copy_status` 回到 `none`。已抽取的全文照常保留（它本来就跟条目走）。
- 删除源（撤销期满后清理）时，条目连同副本一起经外键级联删除。保留期限不删收藏的条目，所以也不删它们的副本。

容量：

- 副本的张数和字节数（`length(body)` 之和）由 `GET /api/storage` 的 `copies`、`copyBytes` 给出，在设置的「活动与存储」里显示。副本在数据库文件里，所以也计入 `databaseBytes`；「压缩数据库」腾出的是删掉副本后留下的空闲页。
