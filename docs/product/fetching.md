# 抓取

抓取循环、订阅发现、RSSHub 路由、WebSub 和正文抽取。索引见 [docs/product.md](../product.md)。

## 抓取

抓取循环跑在服务端进程里，两种运行模式都有，没有单独的 worker。

1. 一组固定的 5 个抓取工作线程不停地取到期（`next_fetch_at` 已到）且未暂停的源，最久没抓的先取，抓完一个马上取下一个，没有「一批」要等齐。一个慢源（最长 25 秒）只占住一个线程，不拖其他源。没有到期的源时每 2 秒左右再看一次，所以新加的订阅最迟几秒内就会开始抓。
   - 同一个主机（主机名加端口）同时最多 2 个请求，两次请求的开头至少隔 1 秒。RSSHub 源发往 `rsshub_base_url` 里的实例，所以受实例所在主机的约束；备用实例在别的主机上时，规则见下面第 3 条。主机忙或还在间隔里时，该主机的源留在到期队列里，线程先去取别的主机的源。
   - 抓取返回 429 或 503 且带 `Retry-After`（解析同下）时，这个主机在这段时间里不再发新的抓取请求，其他主机不受影响；该主机上还没抓的源保持到期，等限制过去再抓，不因此记失败。
   - 抽取正文和清理过期条目各在自己的循环里跑，不占抓取线程，也不等抓取。
2. 带 ETag / Last-Modified 条件请求。超时 25 秒，响应最大 8 MiB，User-Agent 默认 `Oriel/<版本>`（源可以自己填，见[「自定义请求头」](#自定义请求头)）。
3. RSSHub 源用设置 `rsshub_base_url` 加 `rsshub_path` 拼地址，换实例只改设置，改动最迟 2 秒后生效（抓取循环最多每 2 秒读一次这个设置）。没设根地址时这次抓取记为失败。完整的 RSSHub 地址（例如 `https://rsshub.app/bilibili/hot-search`）按普通源抓，用不到根地址；根地址只给只填路由的订阅用。
   - `rsshub_base_url` 可以放多个实例：每行一个根地址（最多 5 个），按优先级排，第一个是主实例。去掉空行和末尾的 `/`，重复的只留第一次出现的。只存一个地址时，它就是只有一个实例的列表。
   - 一个路由按顺序试各实例，第一个答上来的就是结果。**无响应**（连不上、超时、读到一半断开）、**5xx** 和 **429** 是实例的问题，同一次抓取里换下一个实例；其他失败（404、解析失败、响应过大等）是路由的问题，换实例也一样，不再换，按这个实例的结果记失败。
   - 退避按实例，不按源：一个实例失败后进入冷却，期间所有路由都直接跳过它，不再等超时。冷却时长同下面源的退避（该实例连续失败 `n ≤ 5` 次时 60 秒，之后 `min(60 × 2^(n−5), 600)` 秒），带 `Retry-After` 时取较长的；这个实例答上来一次就清零。冷却结束后每个路由先试主实例（列表里最靠前、不在冷却中的），所以主实例恢复后自动回到它。只有一个实例时没有备用可换，不设冷却，失败按源的退避走。
   - 备用实例遵守同样的主机限制：它和当前持有位置的主机相同时用这个位置，不同时要为它自己的主机取一个位置（并发和间隔规则同上），主机忙或还在间隔里就跳过这个实例；用完马上归还。实例失败时它的主机也按冷却时长暂停新请求。
   - 源只在每个实例都失败时才记失败（`consecutive_failures` 加一），`last_error` 按实例写出各自的原因，用 `; ` 隔开，例如 `rsshub.example: status 500; backup.example: status 429`，下一次不早于最早结束冷却的实例。有的实例在冷却或主机忙而没试到、其余的又都没答上来时，这次抓取不记失败也不写 `last_error`，源保持到期，等实例恢复或主机有位置再抓。
   - 抓取成功时 `rsshub_instance` 记下是哪个实例答的；界面在订阅的详情里显示它，看得出现在走的是主实例还是备用。
   - 每个实例的成功率、延迟和是否在冷却，设置里看得到，算法见[「RSSHub 实例健康」](data.md#rsshub-实例健康)。
4. 先把响应体转成 UTF-8：响应头 `Content-Type` 带 `charset` 时按它转（它比 XML 声明优先，转完把声明里的 `encoding` 改成 `utf-8`，免得转两遍），没有就按 XML 声明里的 `encoding`（GBK、ISO-8859-1 等）和字节顺序标记转；`charset` 不认识时当作没有。响应头只在和字节对得上时才算数：响应头写 `utf-8`（或 `us-ascii`）而响应体不是合法的 UTF-8 时，忽略响应头，按 XML 声明转；响应头写的是别的字符集，而响应体是合法的 UTF-8、含非 ASCII 字符、XML 声明写 `utf-8`（或带 UTF-8 字节顺序标记）时，信声明，不再转。UTF-16 的字节顺序标记比响应头优先；没有标记而响应头写 `utf-16`、`utf-16le` 或 `utf-16be` 时按它转（`utf-16` 当小端）；没有标记也没有响应头的 UTF-16 不识别，解析失败按抓取失败记。再解析 RSS、Atom 和 JSON Feed，按 `(source_id, guid)` 写入，guid 换了而链接没变的按「条目」一节的规则认作原来那条。相对链接按订阅地址补全，只留 http 和 https 地址。条目没有自己的作者时，Atom 用订阅级的 `<author>`，JSON Feed 用顶层的 `authors`（1.0 是 `author`）里第一个有名字的；RSS 不做这个回退。
5. 同一次抓到的条目从最后一条往前写，`created_at` 相同时新的条目 `id` 大，在时间线上排前面。
6. 已有的条目只在内容变了时更新，`updated_at` 也只在这时改；已读和收藏不动。标题或正文实质变了时，覆盖之前先把旧版本存成修订（见[「条目的修订」](data.md#条目的修订)）。
7. 文章形态、开着「抓取全文」（`full_text`）的源，新条目 `extract_status` 为 `pending`；其他的为 `skipped`。条目没有摘要也没有正文时，订阅摘要取 `media:description`（含 `media:group` 里的，YouTube 的订阅把简介放在这里）的纯文本，`type="html"` 的先去掉标记；`rss_content_html` 仍为空。
8. Discourse 论坛帖子里引用别人的 `<aside class="quote">` 去掉，免得回帖把别人的话当成自己的正文。订阅摘要（`rss_summary`）是内容的纯文本，一行：文字节点按原样连接，不额外加空格（`<a>moon</a>.` 得到 `moon.`），只有标记里原有的空白、块级元素（段落、标题、列表项、表格行等）的两端和换行 `<br>` 才分词，脚本和样式不算。
9. 源的标题和站点地址为空时，用订阅里的补上。标题还会跟着订阅变：每次成功解析（304 不算）订阅里的标题不为空时，只要源的标题等于 `feed_title`（上次从订阅里取来的值，说明用户没改过），就把标题和 `feed_title` 一起改成订阅里现在的；用户改过标题（标题不等于 `feed_title`）的不动，订阅里的标题再变也不动。标题改成空串仍是「交还给订阅」：下次抓取补上订阅里的，之后又跟着变。`feed_title` 是空串的源：下一次成功解析时，源的标题恰好等于订阅里的标题就记下它（以后跟随），不等就当作用户改过，保持原样，也不记。站点地址只在为空时补，不跟随。
10. 源的图标（`icon_url`）为空时找一次：先用订阅里带的图（RSS 的 `<image><url>`、Atom 的 `<icon>` 或 `<logo>`、JSON Feed 的 `icon`），没有就取站点地址的首页，读 `<link rel="apple-touch-icon">` 和 `<link rel="icon">`，apple-touch-icon 优先，其次 PNG，SVG 和 ICO 不要。首页按「正文抽取」的规则取（只连公网地址，经同一个受限客户端）。找不到就留空，站点地址变了之前不再找。订阅自己带的图（上面「先用订阅里带的图」那几种）还会跟着变：每次成功解析时订阅带了图、并且地址和 `icon_url` 不同，就改成新的；订阅没带图时不动（不会因为订阅不再带图就清空，也不会重新去首页找）。图标不是用户能设的，所以没有「手动改过」要避开。

**永久重定向。** 站点把订阅永久搬走时，Oriel 一直跟着重定向，库里的仍是旧地址：多一跳，旧地址哪天失效就开始失败。服务端记下来，建议用户更新地址，但从不自己改。

- 只看用户填的订阅地址（普通源，包括完整的 RSSHub 地址；只存路由的 RSSHub 源没有订阅地址，换实例走设置）。地址里带用户名或密码的源不建议：新地址不会带凭据，改过去会让抓取失败。
- 算数的是一次成功的抓取（2xx，304 也算）。这次请求从订阅地址一路到终点，每一跳的状态都是 301 或 308 才算永久；有任何一跳是 302、303、307 或别的状态，就不算。终点和订阅地址不是同一个地址（逐字比较，去掉 `#` 片段；所以 `http` 变 `https`、加或去 `www.` 都算搬家，虽然「源」一节的重复比较把它们当成同一个）。新地址可以在别的主机上。跳数的上限和每一跳的 SSRF 检查照常（重定向最多 5 次，从公网跳到本机或内网会被拒绝，见[「代理」](#代理)）：抓取没有成功，就不会有建议，所以新地址一定是通过了同一个受限客户端的。
- 连续 3 次抓取成功、都是永久重定向、都落在同一个新地址，才给建议。每次这样的抓取：终点等于 `moved_url` 时 `moved_seen` 加一，否则 `moved_url` 改成这个终点、`moved_seen` 记 1。抓取成功但没有重定向、或不是永久的，`moved_url` 清空、`moved_seen` 归零（旧地址又直接答了，之前的建议作废）。失败的抓取（含 5xx、超时）不动这几个字段。
- 终点等于 `moved_dismissed`（用户忽略过的）时不记，也不给建议；终点是另一个地址时照常记。`moved_seen` 到 3 且 `moved_url` 不为空，源的 `movedTo` 就是 `moved_url`，否则是空串。
- 接受（`POST /api/sources/{id}/move`）：把 `url` 换成 `movedTo`，清掉 `etag` 和 `last_modified`（它们属于旧地址），清空 `moved_*` 三列的建议，`next_fetch_at` 改成现在。条目、已读和收藏不动：条目按 `(source_id, guid)` 对应，源的编号没变，新地址上的同一批条目认作原来那些。新地址和另一个订阅按「源」一节的规则算重复（或数据库唯一索引拦下）时不改，返回 409 `source_exists` 和那个订阅的编号，建议留着：用户要退订其中一个。
- 忽略（`POST /api/sources/{id}/dismiss-move`）：`moved_dismissed` 记下 `moved_url`，`moved_url` 清空、`moved_seen` 归零。以后这个地址不再提；站点又搬去别的地址，会重新数 3 次。
- 两个接口的请求体都是 `{ "url": "<界面上看到的新地址>" }`，和现在的 `movedTo` 不一致（建议已经变了或没了）时返回 409 `move_changed`，不改任何东西，免得用户按下的是一个过期的地址。

新增订阅（`POST /api/sources`）马上到期。导入 OPML 时，新增的源把第一次抓取摊开：每个源的 `next_fetch_at` 是导入时刻加一个随机延迟，延迟在 `[0, min(10 分钟, 2 秒 × 本次导入的条数))` 内，所以几百个源不会同时到期；只导入一两个时最多等几秒。

每次抓取有了结果（成功、失败，含 304），都在记账之外追加一行抓取记录，见[「抓取记录」](data.md#抓取记录)。抓取工作线程取到一个源就把它记为「正在抓取」，抓完（记账之后）移除；`GET /api/activity` 返回的就是这个集合。每个源还记着三项进度，都只在内存里，抓完就没了：

- 耗时：从工作线程取到这个源到现在，在回答请求时算，所以和客户端的时钟无关。
- 第几次尝试：这一轮抓取发出的第几个实例请求，从 1 开始。只有 RSSHub 路由会大于 1：上一个实例没有回答、回 5xx 或 429，转到下一个实例时加一，在冷却或主机忙而跳过的实例不算。普通订阅一直是 1。这和连续失败的次数（`consecutive_failures`）无关，抓取失败后下一轮重新从 1 算。
- 用的 RSSHub 实例：正在请求的实例，只有主机名和端口；普通订阅没有，还没发出第一个请求时也没有。

成功（含 304）后按 `fetch_interval_sec` 排下一次，清掉失败计数和 `last_error`。

间隔「自动」（`fetch_interval_auto` 为 1）的源，每次成功后先重新算间隔，写进 `fetch_interval_sec`，再排下一次：取该源发布时间（`published_at`）最新的 20 条，只算不晚于现在的，按时间排好，相邻两条的间隔取中位数（间隔个数为偶数时取中间两个的平均），再限制在 15 分钟到 1 天之间。有发布时间的条目少于 5 条（历史太少）时用 15 分钟。固定间隔的源不算，`fetch_interval_sec` 不变。

**全局默认。** 设置里有两项：`default_fetch_interval_sec`（默认间隔，`0` 或没存是「自动」）和 `default_full_text`（新订阅是否抓取全文，默认开）。

- 间隔「自动」的源跟随默认间隔：默认间隔是固定值时，每次成功后把它写进 `fetch_interval_sec` 再排下一次，不再按发布频率算；默认间隔是「自动」时按上一段算。源自己设了固定间隔的不受影响。改默认间隔不动已经排好的下一次，每个源从下一次成功抓取起生效。
- `default_full_text` 只在新建订阅时（`POST /api/sources`、OPML 导入、从其他阅读器导入）写进源的 `full_text`，之后改它不影响已有订阅。OPML 里带 `orielFullText` 的，以它为准。
- 源的 `full_text` 改了只影响之后新到的条目：关掉不撤销已抽取或正排队的，打开不补旧条目。

**形态建议。** 第一次成功抓取（`last_success_at` 此前为空）之后，服务端给 `suggested_kind` 一个建议。先看订阅本身：地址的主机是 v2ex.com 或 linux.do（含子域名），或地址形如 Discourse 论坛的订阅（路径第一段是 `latest`、`top`、`posts`、`c`、`tag`、`tags`、`t`、`u` 之一，文件名以 `.rss` 结尾），或 RSSHub 路由是 `v2ex`、`linuxdo`、`discourse`，建议 `forum`（社区）。不是这些时再看这次抓到的条目：条目不少于 3 条，其中超过一半带时长（`duration_sec`）建议 `video`；否则超过一半带 2 张以上的图建议 `image`；其余没有建议。建议等于当前形态时也不建议。以后的抓取不再改它；用户把形态改成建议的那个后，接口不再下发这个建议。服务端从不自己应用建议。

失败时 `consecutive_failures` 加一，原因写进 `last_error`：连续失败 `n ≤ 5` 次时 60 秒后再试，之后 `min(60 × 2^(n−5), 600)` 秒。一直失败的源不会永远每 10 分钟打扰一次：距离上次成功抓取（从没成功过则距离订阅时间，和「订阅健康」的失效算法同一个起点）已满 3 天，并且已经连续失败至少 5 次（只是暂停或关机了几天、恢复后失败一次不算）时，下一次至少等 6 小时；任何一次成功（含 304）清零失败计数，也回到上面的间隔。这个下限只抬高等待，不改计数；「更新」和 `Retry-After` 照常生效（等待取较长的）。状态码是 429 或 503 且带 `Retry-After`（秒数或 HTTP 日期）时，下一次不早于它指的时刻，即等待取 `Retry-After` 与上面的时间中较长的，最长 24 小时；值无效、为负或已过去时忽略，按上面的时间排。失败照常计数。被拦截和已移除见下面两段。

**已移除（410）。** 响应状态码是 410 Gone，站点在说这个订阅被永久移除。这次抓取照常按失败记（计数、抓取记录不变），`last_error` 写 `status 410: the feed was removed (Gone)`，同时 `last_error_kind` 记 `gone`；下一次成功抓取清掉它。服务端不自己暂停源，也不放弃它：410 偶尔是站点的误答，所以按上面「一直失败」的长间隔继续试，下一次至少等 6 小时，不必等满 3 天。界面看到 `lastErrorKind` 为 `gone` 时建议用户暂停或退订这个订阅，由用户决定（见[「当前界面」](screens.md#当前界面)的「订阅管理」里的「已移除的说法」）。RSSHub 路由上，一个实例答 410 就是路由本身的结论，和 404 一样不再换实例，原因前加实例名。

**被拦截。** 公共的 `rsshub.app` 和不少站点放在 Cloudflare 后面，会把程序的请求当成机器人，答一个挑战页。响应状态码是 403、429 或 503，并且带 `cf-mitigated: challenge`，或者由 `server: cloudflare` 发出、`Content-Type` 是 `text/html`（要订阅却回了网页），就是被拦截。这次抓取照常按失败记（计数、退避、抓取记录都不变），`last_error` 写原始文字（`status 403: blocked by Cloudflare`），同时 `last_error_kind` 记 `blocked`；下一次成功抓取清掉它。RSSHub 路由在每个实例都失败时，只要其中有一个是被拦截，整体也记 `blocked`。Oriel 默认不改 User-Agent（用户可以给单个订阅自己填，见[「自定义请求头」](#自定义请求头)），也不试图绕过挑战：被拦的订阅要换一个不拦的实例，或者用户自己的 RSSHub；填了自定义请求头仍被挑战页拦住的，照常记 `blocked`，不加任何绕过办法。

**失败原因的短语。** `last_error` 存的是原始的英文文字，界面不直接把它当说明：客户端按文字认出常见的几类，换成用户语言的短语，`last_error` 存的仍是原文。分类：超时（`deadline exceeded`、`timeout`）、域名解析失败（`no such host`、`lookup`）、证书错误（`x509`、`tls:`）、连不上（`connection refused`、`connection reset`、`dial tcp`、`EOF`、代理连不上）、状态码 401/403（拒绝访问）、404/410（找不到）、429（被限流，稍后重试）、5xx（站点故障，稍后重试）、`not a feed`（返回的不是订阅内容）。多个实例的原因用 `; ` 隔开时，各段同类才用短语。认不出的原因原样显示；`blocked` 和 `gone` 按 `last_error_kind` 用各自的句子。界面凡是说失败原因的地方都用短语，原文也看得到，屏幕阅读器读短语，并能读到原文。

订阅地址是用户自己填的，可以指向本机或内网（例如自建的 RSSHub），不做 SSRF 检查。订阅内容带出来的地址由正文抽取检查（见下一节）。

没有配置代理（见下面的「代理」）时，抓订阅认 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量，不读系统代理设置。

### 自定义请求头

有些站点（图床、站点自己的 feed）要特定的 `User-Agent` 或 `Referer` 才肯返回内容。每个源可以自己填这两个值，默认空串，不改请求头。

- **只有这两个头。** 界面和接口只收这两个值，没有「头名」，所以没有办法发 `Cookie`、`Authorization` 或别的头：Oriel 不登录原站账号（见产品定位）。服务端也不保存响应里的 `Set-Cookie`，不带 cookie jar。`fetchUserAgent` 以 `cookie:` 或 `authorization:`（不分大小写）开头时拒绝，是拦用户把整行头贴进来。
- **哪些请求用。** `fetch_user_agent` 用于这个源的订阅抓取和它条目页面的正文抽取；`fetch_referer` 只用于订阅抓取。正文抽取的 `Referer` 仍只看 `extract_referer`（见[「正文抽取」](#正文抽取)的「按源规则」），不受 `fetch_referer` 影响。不用于图片代理取图、收藏的本地副本取图、WebSub 订阅请求、订阅发现、RSSHub 路由查找和预览：这些不属于抓某个源的内容，不带 `Referer`。
- **只发给这个源自己的站点。** 请求的主机（主机名加端口）和订阅地址的主机相同时才带这两个头；正文抽取的条目页面在别的主机上时，User-Agent 用默认值。重定向到别的主机时不带，那一跳起 User-Agent 回到默认，也没有 `Referer`；重定向回原主机时再带上。请求照常经过 `guardedClient` 和代理，请求头不改变这些检查。
- **RSSHub 路由没有这两个头。** 只填路由、地址由 `rsshub_base_url` 拼出来的源，请求发往用户自己的实例，不发往上游站点，这两个头对上游没有作用，也不该交给实例：这样的源不能设（`PATCH` 返回 `fetch_headers_unsupported`），界面不显示这一组。填了完整地址的源（包括完整的 RSSHub 地址）按普通源处理。
- **校验。** 去掉首尾空白后：`fetchUserAgent` 是空串，或最长 500 个字符、只含可打印的 ASCII（0x20 到 0x7E）、不以上面两个名字加冒号开头，否则 `invalid_fetch_user_agent`；`fetchReferer` 是空串，或带主机名的 http 或 https 绝对地址、最长 2000 个字符、不带用户信息（`user:pw@`），否则 `invalid_fetch_referer`。空串是不用，回到默认。
- **不是绕过功能。** 填了请求头不改变失败的处理：状态码、退避、`blocked` 的判断都照常，不加重试、不换头再试。
- 请求头的值不是密钥，进备份，接口照常下发；诊断文件和日志里不记它们。改动从下一次抓取起生效。

### 代理

用户可以让抓取经一个 HTTP、HTTPS 或 SOCKS5 代理出去：全局设一个，每个源可以另设或改成直连。

- **全局代理**：设置 `fetch_proxy`，写法 `scheme://host:port`，`scheme` 是 `http`、`https`、`socks5` 或 `socks5h`（两种 SOCKS5 都由代理解析主机名），不带路径、查询串和片段，也不能在地址里写用户名和密码；用户名和密码另存（`fetch_proxy_user`、`fetch_proxy_password`），代理要认证时才设。空串是不用代理。改动最迟 2 秒后生效。
- **按源**：源的 `proxy` 为空串时跟随全局；是 `direct` 时这个源直连，即使设了全局代理，也不认环境变量；是代理地址时这个源用它（和它自己的用户名和密码），不用全局的。
- **哪些请求走代理**：订阅抓取（含 RSSHub 实例的请求，包括备用实例）、正文抽取、WebSub 订阅请求、订阅发现、RSSHub 路由查找和预览、图片代理取图、收藏的本地副本取图。按源的设置作用于这个源的抓取、正文抽取和 WebSub 请求；订阅发现、路由查找、取图和复制图片不属于某个源，只用全局代理（所以一个设为 `direct` 的源，它的图片仍走全局代理）。RSSHub 没有单独的健康探测请求：实例的健康只看抓取结果（冷却、换实例），所以实例的抓取走哪条路，健康检查就走哪条路。
- **不走代理的请求**：AI 摘要和翻译不走这个代理（它们发往用户自己填的接口，常常是本机的模型，也有自己对 `HTTP_PROXY` 的处理）。「导入其他阅读器」（见[「导入其他阅读器接口」](import-export.md#导入其他阅读器接口)）发往用户填的阅读器地址，也不走。
- **用户填的地址**（订阅、RSSHub 实例）：不做 SSRF 检查，照常交给代理。为了自建的 RSSHub 还连得上，主机是本机名 `localhost`、环回地址、内网地址或链路本地地址（直接写成 IP 的）时，不经代理直连；主机名解析到内网的（例如 `rsshub.lan`）不在此列，要把那个源设成 `direct`。这个例外只给用户填的这个地址本身：订阅请求被重定向时，从公网地址跳到上述本机或内网地址会被拒绝（错误同 `ErrBlockedAddress`），不会跟过去。
- **订阅内容带出来的地址**（正文页、WebSub hub、图片、订阅发现）：SSRF 检查仍然有效，代理不能让它们进到内网。连接前 Oriel 自己先解析主机名，任何一个答案是环回、内网、链路本地或保留地址就拒绝（错误同 `ErrBlockedAddress`），解析不出也拒绝；通过后才把主机名交给代理去连（`CONNECT host:port` 或 SOCKS5），每次重定向都再查一遍。已知的限制：代理自己再解析一次，两次答案可以不同（DNS 重绑定），这个窗口 Oriel 看不到，也关不上；信不过代理的用户不要给它内网的访问权。HTTP 和 HTTPS 代理对这些地址一律用 `CONNECT`（包括 `http://` 的页面，端口 80），不允许 `CONNECT` 到 80 端口的代理会让这类请求失败。
- **代理本身**：代理地址可以是本机或内网地址（例如本机的 Clash `127.0.0.1:7890`）；只有它作为配置好的代理时才放行，不会因此放宽对订阅内容里地址的检查。
- **凭据**：代理的用户名和密码是密钥。和 API key 一样只存库里，接口只回是否已配置，不进日志、错误、`last_error`、诊断文件和备份。错误文字里不带代理的地址（也不带它解析出来的 IP 和端口），只写原因（例如 `cannot reach the proxy: connection refused`、`the proxy refused the connection: status 407`）。
- **界面。** 全局代理在「设置 → 抓取」里设。代理地址（空是直连）在回车或离开输入框时保存；用户名和密码在单独的对话框里填，保存时才发，取消什么都不发。用户名和密码只写：接口只回 `proxyAuthSet`，界面只说已配置或未配置，不显示真实的值。删除已存的用户名和密码立刻发送（`proxyUser`、`proxyPassword` 发空串）。改了地址时不发这两项，服务端会把旧的删掉，界面写明这一点。地址不合法（`invalid_proxy_url`）时说明写法，输入不丢。每个订阅（路由订阅也一样）可以选跟随设置（`proxy` 为空串，默认）、直接连接（`direct`）或自定义地址（地址加可选的用户名和密码，规则和全局一样；服务端回 `invalid_proxy` 时报在地址上）。切回跟随或直连时 `proxy` 改了，服务端会删掉这个源存的用户名和密码，客户端不用另外发。
- 备份不含全局代理的用户名和密码，也不含各源的代理用户名和密码（和 API key 一样）；恢复时保留这台服务端自己的全局代理用户名和密码。代理地址本身和 `proxy` 字段照常备份和恢复。

## 订阅发现

给一个网页地址，找出它的订阅。`GET /api/discover`（见[「订阅接口」](api.md#订阅接口)）是服务端的接口，添加订阅用它；它只找，不加订阅，也不写库。

按顺序，找到就停：

1. **内置规则**：地址的主机名（去掉 `www.` 和 `m.`）和路径对上随程序发布的规则表（下面），就直接给出规则里的订阅，不取网页。这些站的页面多半靠脚本渲染或拦截程序，取了也找不到。规则表编在程序里，不在运行时去问 RSSHub Radar 或别的外部服务。
2. **地址本身**：取网页（经 `guardedClient`，只连公网地址，超时 25 秒，最大 8 MiB，同「正文抽取」）。内容能解析成订阅（RSS、Atom、JSON Feed）的，结果就是这个地址本身（`origin` 为 `feed`）。
3. **页面声明**：HTML 里 `<link rel="alternate">` 的 `type` 是 `application/rss+xml`、`application/atom+xml`、`application/feed+json` 且 `href` 可补全成 http(s) 地址的，按页面里的顺序给出（`origin` 为 `alternate`），相对地址按页面地址补全，同一地址只留一个，标题取 `title` 属性。
4. **常见路径**：页面没有声明时，试站点根下的 `/feed`、`/rss`、`/atom.xml`、`/index.xml`、`/feed.json`（`origin` 为 `common`）。只有响应能解析成订阅的才算，按最终地址去重。
5. 都没有：返回空列表，不是错误。

整个发现最多 20 秒，最多取 6 个页面（网页一个，常见路径五个，依次取）。网页本身取不到时仍会试常见路径。页面取不到时 502 `page_unavailable`，地址不是公网地址时 422 `address_not_public`，不是带主机名的 http 或 https 地址时 400 `invalid_url`。内置规则对上时不取网页，所以这三个错误只出现在取网页的步骤。

内置规则（主机名去掉 `www.` 和 `m.`）：

| `youtube.com/@<handle>` | 路由 `/youtube/user/@<handle>` | `video` |

## RSSHub 路由查找

给一个站点链接或站点名，找出用户自己的 RSSHub 实例上能用的路由，填好参数，先预览前几条再订阅。`GET /api/routes` 和 `GET /api/routes/preview`（见[「订阅接口」](api.md#订阅接口)）是服务端的接口，添加订阅用它们；它们只找和预览，不加订阅，也不写库。订阅仍走 `POST /api/sources` 的 `rsshubPath`。

**目录。** 路由目录只读设置 `rsshub_base_url` 里的实例（见[「抓取」](#抓取)），不带在程序里（会过时，也对不上用户实例的版本），也不去问 RSSHub Radar 或 `rsshub.app`：除非 `rsshub.app` 就是设置里的实例，否则不会连它。没设实例就没有目录。实例的 `/api/namespace`（较新的 RSSHub 提供）返回一个对象，键是命名空间，值有 `name`、`url` 和 `routes`；`routes` 的键是路由，值有 `path`、`name`、`example`、`parameters`，可能还有带 `source`（主机和路径的模式）的 `radar`。实例地址是用户自己填的，可以指向本机或内网，和抓取一样不做 SSRF 检查（见[「抓取」](#抓取)）；请求最多 15 秒，响应最大 32 MiB，超出算读不出。

- 宽容解析：不认识的字段忽略；一个命名空间或一条路由解析不了就跳过，不影响别的；`path` 可以是字符串或字符串数组（每个都是一条路由）；命名空间下的路由路径不以 `/命名空间` 开头时补上它。路由模板里的 `:参数`、`:参数?`（可省）、`:参数{正则}`（正则去掉）按出现顺序成为参数，说明取自 `parameters`，没有说明的留空。
- 按实例顺序取第一个读得出的目录；读出来一条路由都没有也算读不出。都读不出（没设实例、实例是旧版没有这个接口、返回的不是 JSON、连不上、超时）时不是错误：接口照常返回 200，`available` 为 `false`，添加订阅退回手填路由，并说明查找不可用。
- 缓存：解析好的目录按实例地址存在服务端内存里，24 小时有效；读不出的结果存 1 分钟，免得边输入边反复去请求。带 `refresh=1` 时丢掉这个实例的缓存重新读。重启服务端后缓存是空的。同一实例同时只读一次，几个请求共用它的结果。

**匹配。** `q` 是用户贴的链接或站点名，不能为空。像地址的（带 `http://` 或 `https://`，或不带协议但有 `.` 且没有空格）按链接匹配，其余按名字匹配。

- 链接按主机匹配（去掉 `www.`，不分大小写）：路由 `radar` 里 `source` 的主机对上，并且路径模式（`:参数` 匹配一段，`*` 匹配其余，`?` 结尾的段可省）也对上的排最前，这时路径里取到的段按同名参数填进 `values`；只有主机对上的次之；命名空间的 `url` 主机对上、而这条路由没有 `radar` 的最后。`source` 的主机可以以 `*.` 开头匹配任意子域名。
- 名字不分大小写，按子串匹配命名空间的键和名称、路由名称和路径。顺序：命名空间名称或键完全相同、以它开头、包含它，然后路由名称包含、路径包含；同档内保持目录里的顺序。
- 最多返回 10 条，`total` 是匹配到的总数，多于 10 条时界面请用户把名字写得更具体。

**预览。** 取填好参数的路由，不订阅：按实例顺序请求 `<实例><路由>`，一个实例连不上、超时或答 5xx、429 时换下一个，答了别的状态码就以它为准（同「抓取」里实例失败的判断）。响应最大 8 MiB，用抓取的同一个解析器读，返回订阅标题和前 5 条的标题、链接和发布时间（没有发布时间为 `null`）。条目为空也是成功。不存条目、不存图标，也不改任何实例的退避状态。

## WebSub 推送

默认关闭。声明了 WebSub hub 的源可以让 hub 在有新内容时主动通知 Oriel，新条目几秒内出现，而不必等下一次轮询。推送只是让源「马上到期」，内容仍由正常的抓取取回；轮询一直都在，推送失效时回到正常的间隔。

**开关。** 设置 `websub_base_url` 是服务端对外可达的公开根地址（例如 `https://oriel.example.com`），hub 要能从公网连到它。没设（默认）时整个功能关闭：不发现、不订阅、不续订，回调路由返回 404，所有源照常轮询。这个地址必须是带主机名的 https 绝对地址，不带查询串和片段，末尾的 `/` 去掉；可以带路径前缀（服务端放在反向代理的子路径下时）。服务端自己不做 TLS，也不替用户开放端口：没设口令时仍只听 `127.0.0.1`（见[「鉴权」](running.md#鉴权)），要收推送得用户自己用反向代理或隧道把公开地址转到本机端口。

**发现。** 开关打开时，每次成功抓到订阅内容（不含 304）就从中找 hub 和主题：HTTP 响应头 `Link` 的 `rel="hub"` 和 `rel="self"`，Atom 或 RSS 里属于订阅本身（不是某个条目）的 `<atom:link rel="hub|self">`，JSON Feed 的 `hubs[0].url` 和 `feed_url`。响应头优先。hub 必须是 http 或 https 地址，主题没有 `self` 时用这次抓取的地址；RSSHub 源也一样处理。hub 或主题和库里的不同就更新，同时作废旧的订阅（状态回到 `''`，下一轮重新订阅）；订阅里不再声明 hub 就清掉。

**订阅。** 后台有自己的循环（不占抓取线程），每 30 秒一轮，每轮最多处理 50 个到了 `websub_next_at` 的源：未暂停、有 hub，且 `websub_next_at` 已到或 `websub_base` 和现在的公开地址不同。流程：

1. 没有时先生成 `websub_key`（16 字节随机，十六进制）和 `websub_secret`（32 字节随机，十六进制），记下 `websub_requested_at`、`websub_base`，再发请求。先写库再发，因为 hub 可能在请求返回之前就来验证。
2. 向 hub 发 `POST`，表单 `hub.mode=subscribe`、`hub.topic`、`hub.callback=<公开地址>/websub/<websub_key>`、`hub.secret`、`hub.lease_seconds=864000`（10 天）。请求经同一个受限客户端发出（hub 地址来自订阅内容，规则同「正文抽取」：只连公网地址，重定向最多 5 次；有代理时经代理，见[「抓取」](#抓取)的「代理」）。
3. hub 回 202 或 204 算受理，之后等验证；`websub_next_at` 设为 10 分钟后，验证没到就重新订阅。其他状态码、连不上、超时都算失败：`websub_failures` 加一，原因写进 `websub_error`，下一次不早于 `min(10 分钟 × 2^(n−1), 24 小时)` 之后。

**验证和推送。** 回调路由 `/websub/{key}` 不要会话（设了口令时也一样），它是唯一不要会话的路由（`GET /health` 和登录除外）；保护靠不可猜的 `key`、逐项核对和签名。`key` 对不上任何源、开关没打开、源已暂停，一律 404。

- `GET`（hub 的验证）：只有 `hub.mode=subscribe`，且 `hub.topic` 等于该源的 `websub_topic`，且一小时内发过订阅请求（`websub_requested_at`）时才接受，否则 404。接受时原样回 `hub.challenge`（`200`，`text/plain`，最长 1000 字符，更长或缺失 400），记 `websub_state=active`，`websub_expires_at = 现在 + hub.lease_seconds`（缺省按 24 小时，最长按 90 天，最短按 60 秒），`websub_next_at = 现在 + 租约 × 0.8`（到点续订，续订就是再发一次 subscribe），清掉 `websub_requested_at`、`websub_failures` 和 `websub_error`。`hub.mode=denied`（同样要核对主题和一小时内的请求）：回 200，`websub_failures` 加一，`hub.reason` 写进 `websub_error`，按上面的退避排下一次，租约还没过期的订阅保持有效。我们从不发 `unsubscribe`，收到它回 404。
- `POST`（推送）：要求状态是 `active` 且租约没过期，否则 404。整个请求体（最大 8 MiB，超过 413）必须带 `X-Hub-Signature: <算法>=<十六进制>`，算法是 `sha1`、`sha256`、`sha384`、`sha512` 之一，用 `websub_secret` 做 HMAC，常数时间比较。签名缺失或不对时按规范回 2xx（202）但整条丢掉，什么都不做。签名对时把源标为马上到期（和「更新」一样，暂停的源不动），回 202；**推送的内容不当作条目**，抓取循环几秒内会照常取订阅，经过同一条路径（条件请求、解析、去重、保留期限）。

**轮询兜底。** 源的 `websub_state` 是 `active`、租约没过期，且开关还开着时，叫「推送中」。推送中的源每次成功抓取后，下一次抓取排在 `min(max(抓取间隔, 6 小时), 租约到期时刻)`；其余情况（没订阅、等验证、失败、租约过期、开关关了、hub 不见了）都按正常的间隔，所以丢了 hub 或续订失败，最迟在租约到期时就回到正常轮询。失败的抓取不受影响，仍按失败退避。用户点「更新」不受推送影响。

不主动退订：源删除（含软删除）、暂停或不再有 hub 时，回调回 404，hub 会因此放弃，租约到期后也自然失效。

## 正文抽取

抽取在自己的循环里，每 5 秒一轮，不等抓取，也不挡抓取：每轮同时抽最多 4 条等待抽取的文章，先取从没试过的（新的在前），再取失败且到了 `next_extract_at` 的。一条抽完（成功或失败）它占的位置马上让给下一条等待的，不等同一轮里其他还在抽的慢页面。同一个网站（主机名加端口）两次请求至少隔 5 秒、同时最多 2 个，一轮里每条文章只试一次，轮到不了的留到下一轮。抽取和订阅抓取共用「抓取」里的每主机限制：同一个主机上正在进行的请求（抓取加抽取）最多 2 个。源后来改成别的形态时，它的条目不再抽。

1. 下载条目链接的网页，超时 25 秒，最大 8 MiB，按响应头和网页声明的编码解码。
2. Discourse 论坛的帖子页只取链接指向的那一楼（`#post_N` 或 `/t/<slug>/<主题>/<N>`，没有就取一楼），并去掉引用块；其他网页用 Readability 取正文。相对链接按最终地址（跟随重定向之后）补全。
3. 成功时 `extract_status` 为 `ok`，写 `extracted_html` 和它的纯文本 `search_text`（进全文索引）；失败为 `failed`。每次都给 `extract_attempts` 加一。失败分两种：
   - 临时的错误：连接失败、超时、读到一半断开，以及状态码 408、425、429 和 5xx。网站可能过一会儿就好，所以晚点再试，间隔越来越长：第 1 次失败后 1 分钟，之后依次 5 分钟、30 分钟、2 小时、6 小时；满 6 次（约 8.5 小时）不再自动重试，`next_extract_at` 清空。状态码是 429 或 503 且带 `Retry-After` 时，等待取它与上面的时间中较长的（解析同订阅抓取，最长 24 小时），并且这段时间里该网站的其他条目也不取。重试时间和网站的暂停都从失败发生的那一刻算起，不是从这一轮开始算起（页面慢了 20 秒才失败，就是 20 秒之后再加等待）。
   - 永久的错误：404、410 等其他状态码、不是 HTML 的页面（`Content-Type` 不是 `text/html` 或 `application/xhtml+xml`）、超过 8 MiB、地址被拦（见下）、抽不出可读正文。等也不会变好，失败一次就不再自动重试，`next_extract_at` 为空。
   用户在阅读器里点「重试」（`POST /api/entries/{id}/extract`）算重新开始：`extract_attempts` 清零、`next_extract_at` 清空、状态回到 `pending`，又有完整的 6 次，下一轮抽取照常取它，仍走同一个受限的客户端。
4. 抽取的结果是派生内容，不改条目的 `updated_at`。

每轮取等待抽取的文章走一个部分索引 `entries_extract_open`（`extract_status, created_at, id`，只含状态为 `pending` 或 `failed` 的条目），所以每轮的代价跟待抽取的条目数有关，不随库里的条目总数增长。

**按源规则。** 自动抽取在个别网站上抓不准，每个源可以有三项自己的规则，在「设置 → 订阅」里这个订阅的页面设置。三项都为空（默认）时，只按上面 1 到 4 步抽取。规则只改变读哪里、请求哪个地址，不改变请求怎么发：所有请求，包括改写后的地址，仍走同一个受限客户端，受下面同样的地址限制。

- `extract_selector`：一个 CSS 选择器，指向正文所在的元素，最长 500 个字符，必须能被解析（cascadia 支持的选择器）。
- `extract_referer`：抽取这个源的网页时带上的 `Referer` 请求头，一个带主机名的 http 或 https 绝对地址，最长 2000 个字符。只发这一个头；不发 Cookie，也不发别的头。
- `extract_rewrites`：改写条目链接的规则，一行一条，最多 10 条，每条最长 500 个字符，写法 `from => to`（`=>` 两边的空白忽略）：
  - **换主机**：`from` 和 `to` 都不含 `/`，写成主机名（可带端口），例如 `m.example.com => www.example.com`。链接的主机名（不分大小写）等于 `from` 时，换成 `to`，协议、路径、查询串和片段不变。
  - **换前缀**：`from` 和 `to` 都以 `http://` 或 `https://` 开头，例如 `https://example.com/amp/ => https://example.com/`。链接以 `from` 开头（逐字比较）时，把这段前缀换成 `to`，后面的部分不变。
  - 两种之外的写法不接受。

有规则时，一条文章的抽取按这个顺序做：

1. **改写**：规则从上到下依次用到条目链接上，后一条看到的是前一条改写后的结果；不匹配的规则跳过。改写不改库里的条目链接，只决定这次抽取请求哪个地址。
2. **请求**：对改写后的地址发请求（有 `extract_referer` 就带上 `Referer`）。改写的结果不是带主机名的 http 或 https 地址，或者被下面的地址限制拦下，这一条的抽取就失败，是永久的失败（不自动重试，用户点「重试」会再走一遍）；不会退回去请求改写前的地址。
3. **选择**：有 `extract_selector` 时，取页面里第一个匹配的元素，它里面的内容（HTML，相对链接按最终地址补全）就是正文，不再跑 Discourse 和 Readability。
4. **选不到就退回自动**：选择器在页面上没有匹配，或者匹配的元素里没有可读的文字，这一条退回上面第 2 步的自动抽取（Discourse，其他用 Readability），并在日志里记一笔。选择器不会让条目变成 `ok`：状态完全由自动抽取的结果决定，抽出来是 `ok`，抽不出来是 `failed`，此时条目照常显示订阅里的内容，不算全文。

规则改了之后，只对之后才抽取的条目生效；已经抽好的条目不重抽。

条目链接来自订阅内容，不是用户填的，所以只能访问公网地址：

- 检查发生在建立连接的那一刻，对象是实际要连的 IP，所以 DNS 解析和每一次重定向都绕不过去。重定向最多 5 次，只能到 http 或 https。
- 拒绝回环、私有网段（`10/8`、`172.16/12`、`192.168/16`、`fc00::/7`）、链路本地（含云元数据地址 `169.254.169.254`）、组播、`0.0.0.0/8`、`100.64/10`、`240/4`，IPv4 映射的 IPv6 地址按 IPv4 判断。
- `198.18.0.0/15` 不拦：Clash 等代理的 TUN 模式会把所有域名解析到这个网段。
- 没有配置代理时直接连接。配置了代理（见[「抓取」](#抓取)的「代理」）时经代理连，但公网检查不放松：连接前先在本机解析主机名并检查所有答案，再交给代理。
