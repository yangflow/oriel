# 时间线规则

节奏、隐藏、文件夹时间线、每日上限、检索语法和规则。索引见 [docs/product.md](../product.md)。

## 节奏

每个源可以设一个「节奏」`pace_sec`：条目在默认时间线里能待多久。快讯几小时就没用了，长文几周后还值得读；没有节奏，两种源的未读都攒在那里，未读数成了读者的负担。节奏**只藏，不删，不改阅读状态**，和保留期限（「保留期限」，删数据）是两回事，互不影响。

预设只有四档，客户端的选择菜单只给这些：

| 名称 | `pace_sec` | 用途 |
|---|---|---|
| 关 | `0` | 默认，条目一直在 |
| 快讯 | 10800（3 小时） | 新闻、快讯、动态 |
| 日更 | 172800（2 天） | 日常的博客和专栏 |
| 周更 | 604800（7 天） | 长文、周刊、播客 |

服务端存的是别的值（3600 到 2592000 之间）时，菜单多一项「N 小时」或「N 天」（整天数用天），照常显示。

规则：条目的时间取列表行上显示的时间，即 `published_at`，没有就用 `created_at`。`pace_sec` 大于 0 时，**未读且未收藏**的条目：

- 到期前最后四分之一的时间（`pace_sec` 的 25%）里**渐隐**：列表行随时间逐渐变淡，到期那一刻最淡（数值见 `design/tokens.md`）。
- 到期（比现在早过 `pace_sec`）后**离开**「全部」和「未读」：`GET /api/entries` 在没有 `source`、没有 `starred=1`、没有 `q` 时不返回它，包括按 `kind` 筛的；它也不计入源的 `unreadCount`；「全部已读」「把上面的标为已读」「把下面的标为已读」不会标到它。
- **留在**检索（`q`）、「收藏」（`starred=1`）和这个源自己的视图（带 `source`）里，在那里不隐藏；在源自己的视图里到期的条目仍然是渐隐的样子，让读者知道它在全部里已经看不到了。源自己的视图里条目会比侧栏的 `unreadCount` 多，这是预期的。
- 已读的条目不受节奏影响（已经读过，不会再攒成负担）；收藏的条目也不受影响。读了或收藏了一个到期的条目，它回到「全部」里它按时间该在的位置。
- 不标已读、不删除、`read_at` 和 `is_read` 不变。改了 `pace_sec` 马上生效，改回 `0` 后条目重新出现。按 `id` 仍能取到和修改。
- 判断用服务端的当前时间，不看客户端的时钟。列表里到期的条目要等下一次刷新列表才消失，不会在打开的列表里自己抽走。

## 不在全部里出现

有些订阅想留着，但不想让它混进主时间线：很吵的站点、偶尔翻一下的资料库、只在需要时才看的源。每个源有一个开关 `hide_from_all`（界面叫「不在全部里显示」，默认关）。和「节奏」一样只藏，不删，不改阅读状态，也不影响抓取：开着的源照常抓、照常保留（保留期限不变）。

开着时：

- 不出现在**全部**和**形态时间线**里：`GET /api/entries` 在没有 `source`、没有 `starred=1`、没有 `q` 时不返回这个源的条目，包括按 `kind` 筛的，「未读」同理。
- **仍然出现**在这个源自己的时间线（带 `source`）、检索（`q`）和「收藏」（`starred=1`）里，在那里不隐藏。
- 同一篇文章合并显示（「同一篇文章只显示一次」）时，隐藏源的条目既不是主条目，也不出现在「另见」里；只有隐藏源转了这一篇时，全部里就没有这一行。在这个源自己的时间线、检索和收藏里不合并，照常显示。
- 未读数：`GET /api/sources` 的 `unreadTotal`（侧栏「全部」、Dock 或托盘角标）和形态按钮上的数不计入隐藏源；这个源自己的 `unreadCount` 照常，侧栏它那一行的数字不变。
- 「全部标为已读」及其变体、「把可见的标为已读」只标当前时间线里显示的条目，所以在全部或形态时间线下不会标到隐藏源的条目；「把订阅标为已读」是这个订阅自己的动作，不受影响。
- 不改 `is_read`、`read_at`；改了开关马上生效，关掉后条目回到它按时间该在的位置。按 `id` 仍能取到和修改。
- 导出的 OPML 在这样的 `outline` 上多一个 `orielHideFromAll="1"`，没开的不写；导入时读到 `1` 就开着。备份是整个数据库的快照，开关随之保存和恢复。

## 文件夹时间线

文件夹（「数据模型」的「文件夹」）也是一个时间线范围，和形态叠加：`GET /api/entries` 和 `POST /api/entries/read` 的 `folder` 参数只看这个文件夹里的订阅，可以同时带 `kind`，那就是「这个形态下这个文件夹的订阅」。

- 文件夹时间线和形态时间线一样是汇总视图：开着「不在全部里显示」的订阅的条目不在其中，到期的节奏条目、超出「每天最多」的条目也按「全部」的规则处理，同一篇文章只显示一次的合并照常。点进订阅自己（带 `source`）、检索（`q`）和收藏（`starred=1`）不受 `folder` 的影响：带了 `source` 时，`folder` 只是再加一个条件。
- 未读数是当前范围的数：客户端把这个范围里订阅的 `unreadCount` 加起来，开着「不在全部里显示」的订阅不计入，和形态按钮上的数一致。接口不另给文件夹的未读数。
- 「全部标为已读」及其变体在文件夹时间线下带 `folder`（和当前的 `kind`），只标这个范围里显示的条目。
- `folder` 不是已有文件夹的编号时 400 `invalid_folder`（`GET /api/entries` 和 `POST /api/entries/read` 一样）。
- 侧栏的组织方式：选了形态时，侧栏列出该形态的订阅并按文件夹分组，没有这个形态订阅的文件夹不显示；在「全部」下，侧栏列出所有文件夹。点文件夹名读它的时间线（当前形态加这个文件夹）；文件夹可以折叠，折叠状态只存在客户端，每台设备各自记；每个文件夹名旁的数是当前范围的未读数。界面的行为见[「当前界面」](screens.md#当前界面)的「时间线」和「文件夹的管理」，外观见界面画布。

## 每日上限

有的源一天发几十条，其中大部分你不会读，又不想退订或整个藏起来。每个源有一个 `daily_cap`（界面叫每天最多，`0` 是关，默认关）：一天里这个源的前 `daily_cap` 条照常显示，之后的条目折成一行，写明条数，点开才展开。和「节奏」「不在全部里出现」一样只藏，不删，不改阅读状态，也不影响抓取：被折叠的条目照常写入、照常保留（保留期限不变）。

- **天**：服务端所在时区的日历日（`time.Local`，本机模式就是你的时区），按条目的写入时间 `created_at` 分，不看 `published_at`。同一个源同一天里按 `(created_at, id)` 从早到晚数，被数到第 `daily_cap + 1` 条及以后的，是超出的。屏蔽词隐藏的条目不占名额，也不会被折叠。
- **只折未读且未收藏的条目**：已读或收藏的条目不会被折叠，但仍占名额。条目被标为已读或收藏时立即展开（`folded` 清成 `0`），之后标回未读也不会自己再折，直到下一次重新计算。折叠状态存在条目上（`entries.folded`，见[「数据模型」](data.md#数据模型)）。
- **什么时候算**：每次抓取写入了新条目之后，对这个源近两天（本地午夜起，往前推一天）的条目重新算一遍；修改 `daily_cap` 时对这个源的所有条目重新算（先全部展开，再按新的上限折叠；改成 `0` 就是全部展开）。重新算时先到的先显示：一天里已经显示的条目不会事后被折掉。
- **在哪里折**：只在没有 `source`、没有 `starred=1`、没有 `q` 的 `GET /api/entries` 里，即「全部」「未读」和形态时间线；这个源自己的视图、检索和「收藏」里所有条目照常显示，不折。折叠的条目仍由 `GET /api/entries` 返回，带 `folded: true`，客户端自己把它们按源和天折成一行；其他情况下 `folded` 不出现。
- **折叠行**：时间线里在被折叠的条目原本所在的位置（它们下一条可见条目的上面）显示一行，写明源的名字和同一个源同一天折叠的条目数；点它、回车或空格展开，展开后这些条目按时间回到列表里，和别的条目一样。界面见[「当前界面」](screens.md#当前界面)的「时间线」。
- **未读数**：被折叠的条目不计入未读数：`GET /api/sources` 里源的 `unreadCount`、`unreadTotal`（侧栏「全部」、Dock 或托盘角标）和形态按钮上的数都不含它们。展开之后条目仍是折叠的状态（`folded` 为 `1`），数字不变，直到它被读或收藏。源自己的视图里条目会比侧栏的 `unreadCount` 多，和「节奏」一样，这是预期的。
- **批量已读**：「全部标为已读」及其变体、「把可见的标为已读」「把上面的标为已读」「把下面的标为已读」只标当前时间线里显示的条目，所以不会标到被折叠的条目（同「节奏」「不在全部里出现」）；「把订阅标为已读」是这个订阅自己的动作，标它所有的未读，包括被折叠的。
- 同一篇文章合并显示（「同一篇文章只显示一次」）不受影响：被折叠的条目照常是合并的一员。
- 导出的 OPML 在这样的 `outline` 上多一个 `orielDailyCap="N"`，没开的不写；导入时读到 1 到 1000 的整数就设上，其他值当没有。
- `daily_cap` 是 0 到 1000 的整数；`PATCH /api/sources/{id}` 的字段 `dailyCap`，错误码 `invalid_daily_cap`（见[「订阅接口」](api.md#订阅接口)）。

## 检索语法

时间线检索框里的文字（`GET /api/entries` 的 `q`）按下面的语法解析。解析在服务端做，接口上是一个 `q` 字符串，加一个可选的 `tz` 参数（见下面日期一条）。语法的解析器是一个不碰存储的纯函数包（`internal/search`），服务端用它出查询，界面用同一个包算要高亮的词，两边不会各认各的。

**词元。** `q` 按空白分成词元。每个词元是下面五种之一，认不出的都是普通词：

| 写法 | 意思 |
| --- | --- |
| `词` | 普通词：标题（含标题的译文，见[「标题翻译」](ai.md#标题翻译)）、订阅摘要或抽取的正文里含有它。不分大小写（只对 ASCII 字母不分，同 SQLite）。 |
| `"整句"` | 短语：含有这一整段文字，空白原样参与匹配。引号里的运算符不起作用，`"from:go"` 就是在找这几个字。 |
| `-词`、`-"整句"` | 排除：含有它的条目不返回。`-` 必须在词元开头且后面紧跟内容；词中间的 `-`（`state-of-the-art`）、单独的 `-` 是普通字符。`--词` 排除的是 `-词`。 |
| `from:名称`、`from:"带 空格 的名称"` | 订阅：订阅的标题含有这段文字（不分大小写的子串）。订阅标题为空时按它的地址算。 |
| `kind:形态` | 形态：`article`、`video`、`social`、`image`、`forum` 之一，不分大小写。 |
| `after:日期`、`before:日期` | 日期范围：日期写成 `YYYY-MM-DD`。`after:2026-01-01` 是那一天零点起（含），`before:2026-02-01` 是那一天零点前（不含）；两个一起用就是一段范围，一月整月写 `after:2026-01-01 before:2026-02-01`。 |

为什么日期用 `after:` 和 `before:`：常见的邮件、代码检索（Gmail、GitHub）都是这一对，只用一种写法，范围就是两个词元叠加，不用另认 `a..b` 或 `2026-01..2026-03` 这样的第二套写法；半开区间让「一整个月」的上下界不用算每月最后一天。

- **日期按哪个时间算。** 按行上显示的那个时间：`published_at`，没有（为 0）就用 `created_at`，同 `olderThan` 的判断。日界按请求里可选的 `tz` 参数（IANA 时区名，如 `Asia/Shanghai`）算：客户端发送系统时区（`time.Local.String()`，值为 `Local` 或空时不发）；缺少或无法识别 `tz` 时退回服务端所在的本地时区，不报错。`tz` 只影响 `after:`、`before:` 的日界。`after` 和 `before` 各出现多次时取交集（取最晚的 `after`、最早的 `before`）；`after` 晚于等于 `before` 时没有结果，不报错。
- **组合。** 不同种类的词元是「并且」。普通词和短语也都是「并且」：`sqlite trigram` 要求两个词都出现，但不要求相邻，也不要求在同一个字段，只要同一条目的标题、摘要或正文里都有。要找连着的整句就加引号。同一种的 `from:`、`kind:` 重复出现是「或」（`from:go from:rust` 是两个订阅里的任一个）。词元最多认 16 个，多出来的忽略。
- **和其他参数。** `q` 里的 `from:`、`kind:` 与查询参数 `source`、`kind` 叠加（都要满足，所以冲突时没有结果）；界面在单个订阅或某个形态的范围里检索时就是这样：`from:` 只会在这个范围里再收窄。`unread`、`starred`、静音和「到期」规则照常叠加。
- **不认识的当普通词，从不报错。** 未知的前缀（`foo:bar`）、`kind:` 后面不是五种形态、日期写错或不存在（`after:2026-13-01`、`before:昨天`）、`from:` 后面是空、没有闭合的引号（引号一直管到结尾）、`""` 空引号（忽略）都不是错误：整个词元按字面当普通词去找，所以 `https://example.com`、`C++`、`12:30` 这样的字符串也搜得到。服务端对任何 `q` 都不答 `invalid_*`、不答 500。
- **转义。** 反斜杠 `\` 只在 `"`、`\`、词元开头的 `-` 前起作用：`\"` 是一个引号字符，`\\` 是一个反斜杠，`\-词` 是以 `-` 开头的普通词；其他位置的 `\` 就是它自己。运算符想当普通词，整个词元放进引号。
- **只有运算符、没有词。** `from:go kind:video` 照常返回，分页同普通列表，没有 200 条的限制；只有排除词（`-广告`）也合法，返回其余全部。`q` 去掉空白后为空才是没有检索。只要 `q` 不为空，不管里面是不是只有运算符，就按「检索」对待：不合并相同链接的条目，到期的条目也返回（见[「节奏」](#节奏)）。

**和分词的关系。** 全文索引是 trigram：任意子串都能命中，不需要分词，所以中文、日文这样不用空格的文字不必切词；`深度学习 模型` 是两个子串，要求都出现。一个词元或短语不足 3 个字符（字数按字符算，如中文常见的两字词 `检索`）时索引匹配不了，这一个词元单独改成对标题和订阅摘要做 `LIKE` 子串匹配（`%`、`_`、`\` 当普通字符，不搜抽取的正文）；排除词同理（`-检索` 只在标题和摘要里排除）。别的词元仍走索引。只要有一个词元走了 `LIKE`，结果就按「短查询」的规则受限：按 `order` 排序，最多 200 条，一次回复就完，`nextCursor` 为 `null`，响应带 `"limited": true`。只有运算符的 `q`、全部词元都够 3 个字符的 `q` 没有这个限制。`from:` 的子串匹配同样不分词，两个字的订阅名也能用，不受这条限制（订阅表很小，用 `LIKE`，不影响分页）。

**高亮。** 高亮在客户端算，接口不返回命中位置。规则：

- 只高亮普通词和短语（含短查询），不高亮排除词，不高亮 `from:`、`kind:`、日期。
- 只在行上画出来的两处：标题，和订阅里的摘要（或没有摘要时的正文片段）。AI 摘要不在检索范围内，不高亮。只在抽取的正文里命中的条目没有高亮，这是预期的，条目照常排在结果里。
- 不分大小写的程度同服务端（只对 ASCII 字母），所以看得到的高亮和命中一致。重叠和相邻的命中合成一段。每个字段最多画 8 段，超出的不画。
- 高亮不改变文字：不增删字符，复制、选字、屏幕阅读器读到的都是原文。屏幕阅读器不报高亮，行的名称不变。

## 规则

规则让一部分新条目自动加星标或标为已读，用来替用户做重复的整理。规则只在新条目到来时执行一次，之后不再碰它。

条件（都填的话要同时满足）：

- 源：若干个源（多选，最多 50 个），或所有源（默认）。条目所属的源是其中之一，才算满足。
- 形态：`article`、`video`、`social`、`image`、`forum` 之一，或不限（默认）。看的是条目所属源的形态。
- 关键词：标题或订阅摘要里包含其中任何一个，匹配和「屏蔽词」是同一个函数（子串、不分大小写、只看标题和订阅摘要）。
- 不含：标题或订阅摘要里包含其中任何一个词，规则就不命中（同一个匹配函数）。和「关键词」是两个独立的列表：规则命中，要满足「含」（若填了）并且不命中任何「不含」。
- 作者：条目的作者里包含这段文字，不分大小写。
- 至少要填一个条件：源、形态、关键词、作者都不填的规则会匹配所有新条目，不接受。「不含」不算条件：只写它的规则会命中几乎所有条目，所以单独一个「不含」仍是 `rule_no_condition`。

动作（可以都选）：

- 加星标：和用户手动加星标一样，条目不被保留期限清理，并排队保存本地副本（见[「收藏的本地副本」](data.md#收藏的本地副本)）。
- 标为已读：条目的 `is_read` 置 1，`read_at` 是写入的时间。

没有「屏蔽」这个动作：隐藏用屏蔽词，因为它能撤销、对旧条目也生效。

何时执行：

- 抓取把一个条目第一次写进库时（`SaveFeed` 里新增的条目），在同一个事务里执行。已有条目被订阅更新、因为换了 guid 而认作同一条、被保留期限挡在门外而没写入的，都不执行。新订阅第一次抓取写入的条目也算新条目。
- 已有的条目不受影响：新建、修改、关掉、删除规则都不回头改任何条目。没有“对已有条目运行”。用户手动改过的状态也不会被规则覆盖，因为规则只在条目刚写入时、用户还没碰过它时执行。
- 不执行的规则：`enabled` 为 0 的；选了源（`rule_sources` 有行）而条目所属源不在其中的；`kind` 不是该源形态的。

顺序和冲突：

- 所有匹配的规则都执行，动作取并集，没有先后：加星标和标为已读互不相干，重复执行同样的动作没有额外效果，所以规则没有顺序，也没有“命中一条就停”。
- 规则同时加星标又标为已读时，条目是已读的收藏。
- 规则加星标的条目不被屏蔽词隐藏（收藏的不屏蔽），即使它也含有屏蔽词。

限制：最多 50 条规则；每条规则最多选 50 个源；关键词和「不含」词各最多 20 行，每行最多 100 个字符；作者最多 100 个字符。

写规则时的命中数：`POST /api/rules/match-count`（见[「规则接口」](#规则接口)）数出按现在填的条件，库里已有的条目有多少条会命中。只数，不改任何条目，也不保存规则，规则照样不回头改已有条目；它只是让用户写关键词时看得到效果，是否过宽一目了然。

### 规则接口

都要会话（设了口令时）。规则在 JSON 里是 `{ "id", "sourceIds", "kind", "keywords", "excludeKeywords", "author", "star", "markRead", "enabled", "createdAt" }`：`sourceIds` 是源的 `id` 数组（从小到大，去重），所有源为 `[]`；`kind` 不限为空串；`keywords` 和 `excludeKeywords` 是按行分隔的一个字符串（和 `muteKeywords` 一样，每行去掉首尾空白，丢掉空行）。

请求里也接受兼容字段 `sourceId`（一个 `id`，或 `null` 表示所有源），只在没带 `sourceIds` 时才看；响应里没有 `sourceId`。

| 路由 | 作用 |
|---|---|
| `GET /api/rules` | `{ "rules": [...] }`，按 `createdAt`、`id` 排，没有为 `[]`。 |
| `POST /api/rules` | 新建，请求体是规则的字段，`enabled` 缺省为 `true`；返回 201 和新规则。撤销删除时可以再带删除前的 `id` 和 `createdAt`（毫秒），规则就回到列表里原来的位置；`id` 已被占用时换一个新的，`createdAt` 仍然保留。 |
| `PATCH /api/rules/{id}` | 只改请求里带的字段，返回改后的规则；合起来仍要满足下面的校验。 |
| `DELETE /api/rules/{id}` | 删除，204；不存在 404 `not_found`。 |
| `POST /api/rules/match-count` | 请求体是规则的条件 `{ "sourceIds", "kind", "keywords", "excludeKeywords", "author" }`（同样接受兼容字段 `sourceId`），返回 `{ "count": n }`：现在库里的条目有多少条满足这些条件（所有没删除的订阅里的条目，不管读过没有、加没加星标，也不管被屏蔽词隐藏与否），匹配和新条目到来时是同一个函数。条件不保存；没有任何条件（「不含」不算）时 `count` 是 `0`。条件不合法时按下面的校验报错（动作不看）。 |

校验，不对的整个请求不生效：

- `invalid_rule_source`：`sourceIds`（或 `sourceId`）里有不存在的源。还在撤销期内的已删除源仍算存在（它或者被恢复，或者被清理时规则随它一起删除），所以此时仍可开关、编辑规则，撤销删除规则也照常。
- `invalid_rule_kind`：`kind` 不是五种形态也不是空串。
- `too_many_rule_sources`：选了超过 50 个源。
- `invalid_rule_keywords`：关键词或「不含」词超过 20 行或某行超过 100 个字符。`invalid_rule_author`：作者超过 100 个字符。
- `rule_no_condition`：源、形态、关键词、作者都没填（只填「不含」也是）。`rule_no_action`：`star` 和 `markRead` 都是 `false`。
- `too_many_rules`：已有 50 条时再新建。
- `invalid_body`：不是 JSON 或类型不对。`PATCH` 的规则不存在时 404 `not_found`。

规则随备份一起走（`rules` 和 `rule_sources` 两张表都在快照里，恢复时按外键的先后次序写回，旧版本的备份在升级时迁移，见[「备份与恢复」](import-export.md#备份与恢复)）。
